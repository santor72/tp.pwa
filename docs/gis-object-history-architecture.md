# Просмотр истории объекта GIS: архитектура

Дата: 16.09.2026. Статус: запланировано, не реализовано.

Это «шаг 2» расширения карточки объекта: прежние фотоотчёты, авторы, даты,
фотографии и опциональная история изменений. Он не совпадает с этапом 2
основного [плана интеграции](gis-implementation-plan.md) и не является
предусловием этапа 3 — отправки отчёта при закрытии заявки.

План реализации: [gis-object-history-implementation-plan.md](gis-object-history-implementation-plan.md).

## Назначение и границы

Монтажник открывает карточку выбранного объекта, затем «Отчёты и фотографии».
Он видит предыдущие отчёты, имя автора, время добавления, текст и фотографии.
Список включает отчёты, созданные как в GIS, так и через внешнюю интеграцию.
Просмотр не изменяет объект, отчёт, статус заявки или отметку «Муфта забита».

История изменений объекта — отдельная необязательная возможность. Она
включается после подтверждения потребности: кто, когда и какие доступные
поля карточки изменил. Полное воспроизведение редактора GIS не требуется.

## Компоненты и доступ

Путь данных: PWA → backend PWA → Integration API GIS → БД и фотоархив GIS.
GIS остаётся владельцем истории и оригиналов фотографий. PWA не создаёт
собственную копию архива. Исходники GIS остаются во внешнем репозитории.

Backend проверяет действующую сессию PWA и использует серверный Bearer-токен
GIS. Браузер получает только URL нашего backend. Ни токен GIS, ни пути к
файлам, ни произвольные внешние URL в ответы не включаются.

На первом этапе все пользователи PWA с доступом к карте видят историю объектов
опубликованных карт. Персональные права GIS не переносятся. Это означает,
что публикация карты для интеграции открывает также её архив отчётов;
владелец GIS должен подтвердить такой объём доступа перед включением.

Для каждого запроса GIS проверяет публикацию карты, актуальность слоя и объекта.
Для фотографии дополнительно проверяется вся цепочка принадлежности:
карта → слой → объект → отчёт → фото. Знание UUID не предоставляет доступ.
Удалённые или неопубликованные объекты возвращают 404. Сверка квитанции
отправки по внешнему ID остаётся отдельным существующим контрактом.

## Предлагаемый контракт чтения

Новые маршруты GIS и соответствующие маршруты backend PWA:

| GIS | Backend PWA | Результат |
| --- | --- | --- |
| `GET /integration/v1/features/{id}/reports?before=…` | `GET /api/gis/features/{id}/reports?before=…` | Страница отчётов |
| `GET /integration/v1/features/{id}/reports/{reportId}/photos/{photoId}` | `GET /api/gis/features/{id}/reports/{reportId}/photos/{photoId}` | Содержимое фотографии |
| `GET /integration/v1/features/{id}/revisions?before=…` | `GET /api/gis/features/{id}/revisions?before=…` | Опциональная история изменений |

Внутренние cookie-маршруты GIS `/api/*` не используются. Существующие
`report-routes.ts` и `web/FeatureHistory.tsx` служат источником семантики;
новые обработчики имеют отдельную проверку сервисного доступа.

### Список отчётов

Ответ: `{ rows: Report[], next: string | null }`, по 20 записей.
Сортировка `created_at DESC, id DESC`; курсор `before` — UUID последнего
отчёта предыдущей страницы. Курсор проверяется на принадлежность объекту;
некорректный или чужой курсор возвращает 400. Новые отчёты не смещают страницы.
Удалённый курсор требует обновить список с первой страницы.

Поля `Report`:

- `id`, `feature_id` — идентификаторы;
- `author_name: string | null` — сохранённое имя автора; для старых записей
  без автора показывается «Автор не указан», без догадок о личности;
- `created_at` — время сохранения GIS в ISO 8601 с часовым поясом;
- `occurred_at: string | null` — время события, если достоверно записано;
- `text` — текст отчёта;
- `source: gis | integration | unknown` — только при подтверждении данными;
- `photos` — список `{ id, mime, width, height, bytes }`;
- `closure_full: boolean` — сохранённая отметка отчёта, если есть.

Не отдавать целиком JSON `attachments`: он содержит служебные идентификаторы,
хеши и другую информацию, не нужную для просмотра. Имена внешних авторов
считаются заявленными интеграцией, а не проверенной учётной записью GIS.
Основная дата в UI — добавление отчёта; время события выводится отдельно,
если отличается. Для старых записей без явного времени события — `null`.

### Фотографии

GIS находит файл только по проверенным UUID и метаданным БД. Разрешены
JPEG, PNG, WebP. Backend передаёт байты потоком, проверяет MIME и ограничивает
размер ответа (первоначально 10 MiB, в соответствии с текущим приёмом фото).
Нельзя доверять только `Content-Length`; ограничение действует и на поток.
Редиректы и URL от клиента не допускаются. При обрыве клиента поток закрывается.

Заголовки: корректный `Content-Type`, безопасный `Content-Disposition`,
`X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`.
API истории и фотографии исключаются из Service Worker Cache Storage.
Фотографии загружаются только при открытии отчёта и по мере появления на экране;
оригинал для увеличения — по нажатию. Миниатюры можно добавить позднее отдельно.

Недоступный объект, чужое фото или неизвестный UUID дают 404. Если запись
есть, но файл потерян/хранилище недоступно — 503 с машинным кодом
`PHOTO_UNAVAILABLE`. Ответ 410 допустим только при наличии явной записи
о регламентном удалении; отсутствие файла само по себе не доказывает истечение срока.

Срок минимального хранения из контракта приёма не означает, что фото удаляется
сразу после его окончания. Реальная сохранность требует постоянного тома или
архива, резервного копирования и проверки восстановления. Этот шаг не вводит
автоматическую очистку фото и не меняет действующий регламент хранения GIS.

### История изменений — опционально

Ответ: `{ rows: Revision[], next: string | null }`, аналогичная пагинация.
Запись содержит `id`, `created_at`, `author_name`, версию и список изменений
`{ field, before, after }`. Разрешены название, описание, слой, оформление,
отметка заполнения; изменение геометрии показывается фактом изменения,
без выдачи полного массива координат каждой исторической версии.

Нельзя возвращать сырые `before/after`: публикуется явный набор полей без
внутренних идентификаторов пользователей, UserSide и служебных данных.
Системные изменения помечаются отдельно. Неизвестное авторство не подменяется.

## Backend и интерфейс PWA

Расширить GIS-адаптер и типизированные маршруты, нормализовать ошибки и задать
тайм-ауты отдельно для JSON и фото. История не влияет на readiness приложения.
401 от GIS — ошибка серверной интеграции, а не повод завершать сессию PWA.
В логи писать request ID, операцию, статус и длительность, без текста отчётов,
имён авторов, токенов и содержимого фото.

В карточке появляется кнопка «Отчёты и фотографии», список открывается лениво.
Состояния: загрузка, пустой архив, ошибка с повтором, страница и «Показать ещё».
Ошибка отдельной фотографии не скрывает текст отчёта и остальные фотографии.
При смене объекта/закрытии панели запросы отменяются, поздний ответ не может
подменить текущую карточку. Поддержать закрытие Escape, возврат фокуса,
клавиатурную навигацию и доступные подписи изображений.

Текст отображается безопасно; импортированный HTML не исполняется.
Просмотр фото и истории не создаёт отчёты и не отправляет сообщения Telegram.
Опциональная «История изменений» появляется только при включении её поддержки
на GIS и backend. Архив фотоотчётов работает независимо от этой возможности.

## Включение и приёмка

Порядок: GIS PR и тестовый деплой → backend → PWA → сквозная приёмка → включение.
Флаг backend для архива выключен по умолчанию до готовности GIS; поддержка
истории изменений управляется отдельно. Клиент получает доступные возможности
от backend. Отключение скрывает архив, сохраняя карту и отправку новых отчётов.

Готовность подтверждается просмотром старого отчёта GIS и отчёта интеграции,
правильными авторами/датами, двумя страницами без дублей, просмотром фото,
корректной обработкой отсутствующего файла и отказом для чужой цепочки UUID.
Проверяется отсутствие фото в offline-кэше и доступа после завершения сессии.
