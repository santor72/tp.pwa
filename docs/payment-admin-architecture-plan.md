# Админка реестра платежей: архитектура и план реализации

## 1. Цель

Добавить отдельный frontend-сервис админки для просмотра успешно принятых
платежей. Доступ разрешён только пользователям ТехПортала со статусом `admin`.

Первый релиз предназначен только для просмотра: он не меняет платёжные
транзакции, не отправляет повторные ссылки и не управляет сущностями Bitrix24.

## 2. Принятые решения

### 2.1. Граница сервиса

В Compose добавляется сервис `admin-frontend` с собственным Nginx-образом и
отдельной точкой входа (в локальном окружении — отдельный порт). Он
проксирует `/api/` в существующий сервис `api`.

В production админка доступна на том же домене, что PWA, но по настраиваемому
базовому пути. Значение `ADMIN_BASE_PATH` задаётся при развёртывании, например:

```env
ADMIN_BASE_PATH=/admin/
# или
ADMIN_BASE_PATH=/sdfsd/
```

Значение должно быть абсолютным путём с начальным и конечным `/`, без `..`,
query-параметров, фрагментов и полного URL. Пустое значение не допускается.
Сервис собирает SPA с этим base path; внешний reverse proxy направляет тот же
путь в `admin-frontend` и настраивает fallback всех вложенных маршрутов на
`index.html`. Статические файлы должны быть доступны внутри этого же пути,
например `/admin/assets/...`.

API не получает префикс базового пути: admin SPA вызывает общий
`/api/admin/...`, а внешний reverse proxy направляет `/api/` в `api` как и для
основного PWA.

Отдельный backend-сервис и отдельная база данных не создаются. Это исключает
дублирование:

- авторизации ТехПортала и серверных сессий;
- доступа к `payment_transactions`;
- миграций и логики статусов платежей;
- секретов Bitrix24.

Схема взаимодействия:

```text
Браузер администратора
        |
        v
admin-frontend (Nginx + SPA) --> api (FastAPI) --> PostgreSQL
                                      |
                                      v
                                  Bitrix24, только существующие процессы
```

Админка использует тот же вход ТехПортала и серверную cookie-сессию. Backend
проверяет роль при каждом admin-запросе; скрытие интерфейса не считается
защитой. Изменяемый путь админки — это маршрутизация, а не мера защиты доступа.

### 2.2. Доступ

В `Capabilities` добавляется `payment_admin`:

```text
payment_admin = user.role == admin
```

Все маршруты `/api/admin/payments...` требуют роли `admin` независимо от
значения любых точечных `permissions`. Пользователь с ролью `manager` или
`user` получает `403 PERMISSION_DENIED`.

### 2.3. Определение принятого платежа

Реестр по умолчанию показывает только записи:

```text
payment_transactions.status = "paid"
```

Дата оплаты — `paid_at`, а не дата создания ссылки. Все границы фильтра
интерпретируются в часовом поясе `Europe/Moscow` и на backend переводятся в UTC.

Период по умолчанию — последние 30 календарных дней, включая текущий день.

## 3. API

### 3.1. Список платежей

```text
GET /api/admin/payments
```

Параметры запроса:

| Параметр | Формат | По умолчанию | Назначение |
|---|---|---:|---|
| `date_from` | `YYYY-MM-DD` | 30 дней назад | Начало периода, МСК |
| `date_to` | `YYYY-MM-DD` | сегодня | Конец периода, МСК |
| `phone` | строка | — | Частичный номер клиента; перед поиском остаются только цифры |
| `employee` | строка | — | Поиск по имени сотрудника или `employee_external_id` |
| `page` | целое >= 1 | `1` | Номер страницы |
| `page_size` | 1..100 | `50` | Размер страницы |

Сортировка фиксирована: `paid_at DESC`, затем `id DESC` для стабильной
пагинации.

Ответ содержит `items`, `page`, `page_size` и `total`.

Каждый элемент списка включает только необходимые для реестра поля:

- локальный ID операции;
- `paid_at`, сумму, валюту, товар и статус;
- телефон и e-mail клиента;
- имя сотрудника и его ID ТехПортала;
- ID лида, контакта, счёта и платежа Bitrix24;
- название платёжной системы.

Платёжная ссылка и QR-код в ответы админки не включаются.

### 3.2. Карточка платежа

```text
GET /api/admin/payments/{transaction_id}
```

Возвращает данные одной операции и безопасную историю событий из
`payment_transaction_events`. В карточке не возвращаются платёжная ссылка,
QR-код, webhook-токены или технические ответы Bitrix24.

## 4. База данных и поиск

Все нужные поля уже есть в `payment_transactions`: `paid_at`, статус, телефон,
сотрудник, сумма, товар и Bitrix24 ID.

Добавить миграцию с индексами:

```text
status, paid_at DESC
employee_external_id, paid_at DESC
```

Поиск по телефону в первом релизе выполняется по очищенной строке номера.
Если объём реестра сделает его заметно медленным, следующим изменением станет
`pg_trgm` и GIN-индекс на `phone_normalized`; это не требуется заранее.

## 5. Интерфейс

Экран админки содержит:

1. форму фильтров: период, телефон клиента, сотрудник, кнопки «Применить» и
   «Сбросить»;
2. таблицу: дата оплаты, товар, сумма, клиент, сотрудник, платёжная система,
   Bitrix24 счёт/платёж;
3. итог количества найденных записей и постраничную навигацию;
4. состояния загрузки, ошибки и пустой выдачи;
5. открытие карточки операции по нажатию на строку.

Админка не показывает кнопки отмены, повторной отправки, формирования платежа
или изменения данных.

## 6. Безопасность и аудит

- Backend проверяет роль `admin` для каждого списка и карточки.
- Login, logout и любые будущие изменяющие действия используют текущую
  CSRF-модель; read-only GET запросы используют серверную сессию.
- В аудит пишутся ID администратора, тип просмотра, параметры без персональных
  значений и число найденных записей. Телефон, e-mail, ФИО, платёжная ссылка и
  QR-код в логи не попадают.
- Актуальная роль берётся из последнего входа в ТехПортал. При изменении роли
  пользователю требуется войти заново.

## 7. План реализации

### Этап 1. Контракты и серверный доступ

- [ ] Добавить `payment_admin` в schemas, capabilities и ответы сессии.
- [ ] Реализовать единый dependency/guard роли `admin` для admin API.
- [ ] Добавить схемы запросов фильтра и ответов списка/карточки.
- [ ] Добавить аудит чтения реестра и карточки без персональных данных.

Критерий готовности: не-администратор не видит capability и получает `403` при
прямом обращении к каждому admin endpoint.

### Этап 2. Репозиторий и миграция

- [ ] Добавить SQL-запрос списка оплаченных операций с фильтрами и `total`.
- [ ] Реализовать стабильную сортировку и валидацию пагинации.
- [ ] Реализовать получение одной операции с безопасной историей событий.
- [ ] Добавить миграцию индексов `status/paid_at` и
  `employee_external_id/paid_at`.

Критерий готовности: выборка правильно обрабатывает московские границы дат,
часть телефона, имя/ID сотрудника и не включает неуспешные операции.

### Этап 3. HTTP API и тесты

- [ ] Добавить `GET /api/admin/payments`.
- [ ] Добавить `GET /api/admin/payments/{transaction_id}`.
- [ ] Написать тесты авторизации, фильтров, сортировки, пагинации и отсутствия
  в ответах ссылок/QR.

Критерий готовности: API покрыт тестами и возвращает только разрешённый набор
полей.

### Этап 4. Отдельный frontend-сервис

- [ ] Создать отдельное frontend-приложение или независимую точку сборки
  `admin-frontend` с собственным Dockerfile и Nginx-конфигурацией.
- [ ] Добавить и валидировать `ADMIN_BASE_PATH`; передавать его в сборку SPA и
  Nginx-конфигурацию admin-сервиса.
- [ ] Добавить сервис в `compose.yaml`, `compose.prod.yaml.sample`, health-check
  и документацию с шаблоном правила внешнего reverse proxy для
  `ADMIN_BASE_PATH`.
- [ ] Реализовать вход, проверку `payment_admin` и экран отказа в доступе.
- [ ] Реализовать форму фильтров, таблицу, пагинацию и карточку операции.

Критерий готовности: сервис запускается независимо от PWA, а `/api/`
проксируется в существующий backend; изменение `ADMIN_BASE_PATH` не требует
правки исходного кода и сохраняет работу прямых ссылок и статических файлов.

### Этап 5. Приёмка

- [ ] Запустить backend и frontend тесты.
- [ ] Собрать все контейнеры и применить миграции на чистой и существующей БД.
- [ ] Проверить реальным admin-пользователем ТехПортала доступ и выборку
  тестовой успешной оплаты.
- [ ] Проверить пользователями `manager` и `user` скрытие UI и ответ `403` API.
- [ ] Обновить пользовательскую и эксплуатационную документацию.

## 8. За рамками первого релиза

- Экспорт реестра в CSV/XLSX.
- Фильтрация и отдельный список неуспешных, отменённых или ожидающих операций.
- Групповые итоги по сотрудникам, товарам и платёжным системам.
- Ручные действия с оплатой из админки.
- Триграммный индекс номера телефона при подтверждённой необходимости.
