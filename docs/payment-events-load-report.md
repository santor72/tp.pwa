# Нагрузочные проверки событийных обработчиков

Статус: частичная проверка критериев плана, не разрешение на рабочее переключение.

## Обнаружение после пустого обхода — 2026-09-13

`test_payment_polling_deadlines.py`: **2 passed за 2,18 с**. Настоящий Postgres;
в первом сценарии работает relay.run с отключённым LISTEN/NOTIFY и тестовым
publish, во втором recovery.run с настоящим executor и тестовым бизнес-сервисом,
без какого-либо Redis client. Создание оплаты начинается после завершения
пустого обхода. Настроенный интервал обоих тестов 0,2 с; заранее заданный gate —
интервал плюс 0,5 с на БД и планирование процесса.

Измеряется верхняя оценка от начала сохранения оплаты (до commit) до публикации
или входа в бизнес-сервис: relay **0,222 с**, fallback **0,280 с**. Так время
commit не исключается в пользу результата. Оба значения ниже 0,7 с.
Это проверка управляемого polling interval на свободном тестовом стенде, не
обещание фиксированной задержки при backlog и не замер продуктивного интервала
fallback 30 с. Сетевой вызов Битрикса и длительность появления QR не измеряются.

## Стенд и методика

Тест `backend/tests/test_payment_events_scaling.py` использует отдельные процессы
Python (spawn), реальные Postgres 16 и Redis 7.4 из
`compose.payment-events-test.yaml`. Каждый процесс создаёт собственные соединения,
PaymentConsumer, PaymentJobExecutor и Bitrix24Client. Группа formation общая,
имена consumer разные. Схема БД и префикс Stream уникальны для тестового запуска.

Битрикс заменён HTTP MockTransport с задержкой 80 мс. У задания одна внешняя
запись, проверяемая журналом внешних действий и общей тестовой очередью вызовов.
Время прогрева процессов и предварительной публикации backlog не входит во время
обработки 48 заданий. Бюджет запросов для этого теста намеренно не ограничен:
проверяется масштабирование исполнителей, а не пропускная способность портала.

При 1/2/4 процессах проверяются: завершение всех 48 заданий, участие каждого
экземпляра, соответствие внешних вызовов уникальным операциям, подтверждённые
записи журнала, штатная остановка процессов. Критерий 1→2 — сокращение времени
минимум на 30%; дополнительно требуется улучшение 2→4.

Отдельная фаза с одним прогретым процессом и работающим relay последовательно
создаёт 100 одиночных операций без backlog. Измеряется интервал от начала
транзакции приёма до захвата задания, то есть консервативная верхняя оценка
commit → начало executor. Relay использует LISTEN/NOTIFY и штатный опрос 1 с.
Критерий p95 ≤ 1 с не относится ко времени появления QR.

## Воспроизведение

Включить только изолированный тестовый Compose-проект. Его опубликованные порты
узнать через `docker compose -p tp-payment-events-test -f compose.payment-events-test.yaml
port postgres 5432` и аналогично для Redis. Не использовать URL рабочего приложения.

Из `backend` запустить:

```bash
PAYMENT_EVENTS_LOAD_TEST=1 \
PAYMENT_EVENTS_TEST_DATABASE_URL=postgresql+asyncpg://events_test:events_test@127.0.0.1:<порт-PG>/payment_events_test \
PAYMENT_EVENTS_TEST_REDIS_URL=redis://127.0.0.1:<порт-Redis>/0 \
PYTHONPATH=. .venv/bin/pytest -q -s tests/test_payment_events_scaling.py
```

Угловые скобки заменить фактическими номерами портов перед запуском.
По умолчанию этот тест пропущен: нагрузка разрешается отдельной переменной.
Вывод содержит `SCALING_RESULT` и `IDLE_RESULT`; падение любого критерия делает
прогон неуспешным. Автоматическое завершение удаляет только UUID-схему и свой
Stream; не выполняет очистку всей БД или Redis.

## Принудительная остановка после внешней записи

`test_t09_t10_t23_sigkill_after_remote_write_recovers_without_duplicate` использует
два последовательно запускаемых процесса и общий fake-журнал Битрикса, живущий
отдельно от них. Первый процесс сохраняет in-flight попытку в PostgreSQL;
fake принимает создание контакта, но не возвращает HTTP-ответ. После проверки
этого состояния тест посылает SIGKILL только созданному тестовому процессу.

Новый процесс перехватывает pending сообщение, ждёт истечения настоящего lease
(в тесте 2 с, без ручного изменения времени БД), ищет контакт по ORIGIN_ID,
подтверждает journal новым fencing token и завершает задание. Проверяется ровно
один write и один read во внешнем fake, подтверждённая запись журнала и pending=0.

Результат отдельного прогона: **1 passed за 6,33 с**, восстановление после SIGKILL
**2,314 с**, remote writes=1, pending=0. Тестовый timeout восстановления — 8 с:
короткий lease + конечный цикл reclaim + запас на запуск нового процесса.
Он не заменяет измерение с production-настройкой lease 90 с и не доказывает
восстановление всех типов CRM write или задержанной видимости поисковых результатов.

## Изоляция от очереди старых сверок

`test_t25_reconciliation_backlog_does_not_delay_new_formation` запускает отдельные
процессы formation и reconciliation, каждый читает свой Stream/group. Сначала
публикуются 48 сверок существующих операций. После первого фактического HTTP
чтения статуса создаётся новая оплата и публикуется её formation-событие.

Первый прогон: **1 passed за 4,92 с**, новая оплата обработана за **0,293 с**,
в очереди сверок оставалось **45** заданий. Проверяются обе работающие роли,
завершение нового задания до опустошения старой очереди и штатная остановка.
Порог для этого стенда — менее 1 с, без ограничения общего бюджета запросов.
Сверки используют production транспорт/executor/client, но тестовый обработчик
с одним HTTP read; это не полный сценарий PaymentStatusHandler.

Совместный повтор всех трёх многопроцессных тестов: **3 passed за 51,69 с**.
Изоляция: 0,288 с и 45 оставшихся сверок. SIGKILL: 2,312 с, один write,
pending=0. Масштабирование: 7,067 / 3,652 / 1,799 с; idle p95 по 100 операциям
0,041 с. Все численные критерии этого набора выполнены.

## Границы доказанного

Это не измерение полной цепочки создания оплаты и не прогноз реального времени
QR. Прогон использует production consumer/executor/Bitrix client, но тестовую
бизнес-операцию и не проверяет entrypoint runtime, Compose scale, лимитер,
ограниченный общий бюджет запросов или отказ Redis. Изоляция backlog и SIGKILL проверены отдельно
для одного вида внешней записи, как описано выше. Остальные проверки остаются
самостоятельными пунктами T23–T25 и итогового аудита.
