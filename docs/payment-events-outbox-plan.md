# План реализации событийной обработки платежей: outbox и Redis Streams

Статус: реализация начата, критерии завершения ещё не выполнены. Дата: 2026-09-11.
Ход работ и фактические проверки: [payment-events-implementation-report.md](payment-events-implementation-report.md).
Сводная сверка требований: [payment-events-acceptance-audit.md](payment-events-acceptance-audit.md).
План пригоден для последовательного выполнения в Goal. Создание этого документа
не означает запуск Goal или разрешение на реальные операции в Битриксе.

Формулировка задачи для Goal: «Реализовать этот план: сначала определить и
проверить тесты с ожидаемыми результатами, затем внедрить outbox, разделение
обработчиков и их независимое масштабирование. Проверки выполнять на
изолированном стенде с fake Битрикс. Сохранить отчёт о выполненных проверках
и оставшихся ограничениях; рабочее развёртывание не выполнять».

## 1. Сначала тесты и ожидаемые результаты

До изменения маршрутов обработки написать тесты по матрице ниже. Для нового
поведения сначала получить ожидаемые падения, затем добиваться прохождения
по этапам. Тесты гонок и транзакций выполнять на настоящих изолированных
Postgres 16 и Redis 7.4, а не на SQLite. Битрикс во всех автоматических тестах
подменяется HTTP fake с учётом созданных сущностей и управляемыми сбоями.
Не использовать рабочие БД/Redis, не очищать их и не отправлять реальные SMS.

| T29 | PostgreSQL недоступен | Нельзя принять оплату без сохранения; worker не выполняет внешние записи без проверки владения; сообщение не подтверждается как выполненное |

### 1.2. Измеримые критерии приёмки

- На контролируемом стенде без backlog и с быстрым fake Битрикс: из 100 операций
  p95 от commit оплаты до начала executor не больше 1 секунды при рабочих событиях.
  Это тест запуска, а не обещание времени появления QR на реальном портале.
- При потере NOTIFY доставка обнаруживается не позже интервала опроса outbox
  плюс время запроса/публикации. Начальный интервал — 1 секунда.
- При недоступном Redis свободный fallback обнаруживает готовое задание не позже
  интервала fallback (начально 30 секунд) плюс время запроса/захвата.
  При backlog и занятом lease отдельно измеряется ожидание ресурсов.
- После гибели worker: восстановление не позже оставшегося срока lease плюс
  интервал обхода восстановления и время сверки неизвестного внешнего результата.
- В нагрузочном тесте с отключённым узким лимитом fake увеличение 1→2 worker
  уменьшает время обработки одинакового backlog минимум на 30%; затем отдельно
  тестировать ограниченный бюджет Битрикса, не требуя линейного ускорения.
- Для каждого теста падения: ни потерянных логических заданий, ни повторных
  внешних сущностей в моделируемом сценарии; неразрешимый неизвестный результат
  попадает в видимое состояние ручной сверки, а не скрывается как успех.
- Все существующие тесты resolver, платежей, прав, API, frontend и репозиториев
  продолжают проходить. Миграции проверены upgrade/downgrade на изолированной БД.

## 2. Цель и границы

Заменить смешанный периодический worker событийной обработкой с transactional
outbox, независимыми группами формирования и сверки статусов, безопасным
горизонтальным масштабированием и восстановлением из Postgres.

Существующие бизнес-правила поиска контакта/лида, дополнения телефона/email,
наследования адреса, суммы и товара не менять. Сохранить журнал операций,
право tickets.execution и административные проверки. Ссылка/QR по-прежнему
доступны сразу после сохранения, до завершения комментариев и отправки.

Этот план актуальнее старого payments-goal-plan.md в части организации worker.
Другие исторические допущения того документа не переносить поверх текущего кода.
Диагностика: [payment-timing-diagnostics.md](payment-timing-diagnostics.md).

## 3. Архитектура и гарантия доставки

```text
API / callback / планировщик
        │ одна транзакция
        ▼
Postgres: payment + job + outbox
        │ NOTIFY ускоряет; опрос страхует
        ▼
outbox-relay → Redis Streams
                 ├─ formation group → N formation worker
                 └─ reconciliation group → M reconciliation worker

Postgres → recovery/fallback → тот же executor и тот же lease
```

Два Stream с префиксом окружения: `<prefix>:payments:formation` и
`<prefix>:payments:reconciliation`. Consumer group отдельная для каждого потока;
у каждого процесса уникальное имя consumer. Старт с N=1, M=1, relay=1.
Масштабирование relay также допускается, но не требуется для первого запуска.
Не заводить отдельную consumer group на каждый экземпляр: это изменит семантику
с распределения работы на независимое чтение каждым экземпляром.

Доставка at-least-once. Не обещать exactly-once внешних вызовов: Redis ACK,
Postgres commit и вызов Битрикса не образуют общую транзакцию. Fencing token
защищает наши записи, но Битрикс его не проверяет. Для внешних записей обязательны
устойчивые маркеры, журнал попыток и обработка неизвестного результата.

### 3.1. Содержимое сообщения

```json
{
  "event_id": "uuid",
  "job_id": "uuid",
  "transaction_id": "uuid",
  "event_type": "payment.formation_requested",
  "schema_version": 1,
  "generation": 1
}
```

Только идентификаторы и техническая версия. ФИО, телефон, email, webhook-секреты,
адрес и платёжные ссылки в транспорт не помещать. Сопоставление event/job/payment,
тип и generation проверять по Postgres; Stream не является источником полномочий.

### 3.2. Состояние в Postgres

Предлагаемые новые таблицы; точные имена колонок утвердить миграцией этапа 2:

- `payment_jobs`: id, transaction_id, kind, generation, state, available_at,
  attempt_count, last_safe_error, created_at, finished_at. Состояния ready,
  running, retry_wait, completed, superseded, failed, needs_reconciliation.
  Уникальность логического задания задаётся business key (оплата, тип, generation).
- `payment_outbox`: event_id, job_id, event_type, schema_version, available_at,
  publish_attempts, next_publish_at, publisher_token, publisher_lease_until,
  last_published_at, stream_message_id, completed_at, created_at.
  Отправка и выполнение — разные отметки. Строки не удаляются при XADD.
- `payment_execution_leases`: transaction_id (PK), owner, fencing_token,
  lease_until. Единый lease на оплату для обеих групп и fallback.
- Журнал внешних write-попыток: оплата, шаг, устойчивый marker, состояние
  prepared/in_flight/confirmed/unknown, remote_id, timestamps, fencing_token.
  Не сохранять сырые тела с персональными данными ради диагностики.
- Таблица/строка общего бюджета запросов к каждой интеграции Битрикса.

Внешний HTTP выполняется вне транзакции БД. Захват/продление и сохранение результата
короткие, с проверкой token. Индексы на готовность, lease_until, связь job/outbox
и незавершённые задания. Время lease/available_at считать по часам Postgres.

## 4. Правила исполнения и восстановления

### 4.1. Доставщик outbox

1. Выбрать готовые строки с FOR UPDATE SKIP LOCKED, назначить publisher lease,
   завершить транзакцию; не захватывать большую пачку, которая протухнет до отправки.
2. Выполнить XADD; после успеха отдельно сохранить stream_message_id и время
   публикации при совпадении publisher token. Не отмечать job выполненным.
3. При ошибке публикации назначить ограниченный exponential backoff с jitter.
4. LISTEN работает на выделенном соединении, вне долгих транзакций. После
   подписки/переподключения — сканирование outbox, затем ожидание сигнала/таймера.
5. NOTIFY в транзакции создания outbox содержит только сигнал пробуждения.
   available_at в будущем всё равно требует периодического обхода.

Уведомления доставляются после commit; они не заменяют постоянную очередь.
См. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html).

### 4.2. Consumer и ACK

Использовать XREADGROUP с ограниченным BLOCK и небольшим COUNT, без NOACK.
Группа создаётся идемпотентно с MKSTREAM и чтением накопленных сообщений с 0.
См. [Redis XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/).

- Получить job из Postgres, проверить event и состояние, захватить lease оплаты.
- Если job уже завершён/устарел — XACK без выполнения CRM-действия.
- Если lease занят — не ACK как успешное выполнение; оставить сообщение для
  последующего восстановления без активного кручения цикла.
- Выполнить общий executor; heartbeat продлевает lease только текущим token.
- Атомарно сохранить прогресс, исход job и необходимые следующие jobs/outbox,
  затем XACK. Ошибка XACK после commit безопасна при повторной доставке.
- Для бизнес-повтора атомарно завершить текущую попытку и создать следующее
  задание с available_at, затем ACK текущего сообщения. Не спать в consumer
  до наступления срока и не смешивать retries доставки с retries Битрикса.
- Pending сообщения погибших consumer перехватывать через XAUTOCLAIM, обходить
  весь cursor с лимитом работы за проход. Idle-time Redis не является правом
  выполнения: решает lease Postgres. См. [Redis XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/).
- Некорректные сообщения записывать в ограниченный quarantine/DLQ с безопасной
  причиной; ACK только после надёжной фиксации этой причины. Не логировать raw body.

### 4.3. Неизвестный результат внешней записи

До CRM write сохранить маркер попытки, после ответа — результат. Если ответ
потерян, сначала искать уже созданную сущность/связь. Если поиск пока ничего
не возвращает, учитывать задержку видимости: отсутствие результата одного
чтения не доказывает, что создание не произошло. Для шага без достаточной
идемпотентности остановить автоматический повтор в needs_reconciliation и
поднять alert. Не пытаться добиться доступности ценой дублей платежей.

Проверять владение перед каждым новым внешним шагом. При потере heartbeat
не начинать следующие записи; уже отправленный запрос считать потенциально
выполненным, даже если удалось отменить локальную coroutine.

### 4.4. Fallback и планировщик

Recovery периодически ищет по Postgres: готовые задания без прогресса доставки,
протухшие lease, наступившие retries, очередные сверки, истечения срока оплаты.
Создание следующего логического задания идемпотентно, защищено блокировкой/unique.

Если Redis работает — повторно публикует событие того же задания, не создавая
бесконечные поколения из-за одной задержки доставки. Если события не приводят
к прогрессу или Redis недоступен — исполняет job напрямую через тот же executor.
Direct fallback имеет отдельные formation/reconciliation режимы и ограниченную
конкурентность, чтобы не вернуть смешанную очередь. Общие leases и лимитер
обязательны. Старый process_once не запускается параллельно как запасной путь.

Сверки отменённых/просроченных операций и поздних callback должны сохранять
действующие правила признания paid; нельзя blanket-правилом игнорировать все
события для любых terminal states. Unknown payment_id callback сохранять как
ограниченный запрос сверки по ID, пока он не сопоставлен с оплатой или не истёк
срок ожидания: callback может прийти раньше сохранения bitrix_payment_id.

### 4.5. Общий бюджет запросов Битрикса

Для первого варианта использовать единый ограничитель в Postgres по идентификатору
интеграции (без хранения webhook в ключе), чтобы Redis outage не отключал fallback.
Короткая транзакция резервирует слот/токен; ожидание происходит вне транзакции.
Учитывать запросы API, обеих групп, fallback и внутренние попытки Bitrix24Client.
Проверить стоимость такого лимитера нагрузочным тестом; Redis-оптимизация —
отдельное улучшение, не два независимых бюджета с суммарным превышением.

RPS/burst и общий cooldown после 429 настраиваются; не объявлять произвольные
значения фактическим лимитом портала. Начальный бюджет согласовать с измерениями
и условиями интеграции до увеличения числа worker. Сверка не должна вытеснять
формирование полностью, и наоборот: тестировать справедливое распределение.

## 6. Откат и завершение

Откат — переключение на совместимый DB-polling executor, а не запуск старого
бинарника рядом с event consumers. Сначала остановить новые readers/relay/fallback,
дождаться освобождения leases, проверить неизвестные CRM-записи, затем включить
совместимый legacy режим. Он обязан понимать новые задания и pending selections.
Не удалять новые таблицы для оперативного отката и не терять принятые команды.
Если возврат требует старого образа, сначала выполнить отдельный проверенный
план совместимости данных; автоматический downgrade в production запрещён.

Готово, когда все этапы отмечены, тесты и отчёт приложены, секретов нет в логах,
новые обработчики независимо масштабируются, сбои Redis/worker восстанавливаются
из Postgres, а оператор видит неразрешённые состояния. Любое исключение из матрицы
явно документировать; пропуск теста не считать успешным результатом.
