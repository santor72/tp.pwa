# Принятые архитектурные решения

## Назначение

Приложение предназначено для разъездных специалистов интернет-оператора.
На текущем этапе разрабатывается PWA с авторизацией через учётную запись
ТехПортала и рабочим разделом «Домофон».

## Границы текущего этапа

В текущий этап входят:

- PWA-интерфейс;
- авторизация пользователя через ТехПортал;
- собственная серверная сессия приложения;
- обработка истечения и отзыва пользовательской сессии;
- раздел «Домофон»;
- заявки на сегодня и завтра;
- backend-интеграция с REST API;
- структурированное логирование входов и действий пользователя;
- передача контейнерных логов в Vector;
- Redis для серверных сессий и кэширования;
- автоматические тесты.

Не входят в текущий этап:

- подключение услуг;
- работа с оборудованием;
- Telegram-бот и другие пользовательские адаптеры.

Telegram-бот принят как следующий этап после PWA. Архитектура общей
подсистемы мессенджеров и Telegram-адаптера зафиксирована в
[`docs/messengers-architecture.md`](messengers-architecture.md). Поэтапная реализация описана в
[`docs/messengers-implementation-plan.md`](messengers-implementation-plan.md).

Нереализованные разделы не показываются в рабочем интерфейсе. Демо-заглушки,
фиктивные токены и ответы, имитирующие успешные операции, запрещены в рабочем
коде.

## Общая архитектура

```text
PWA
 │
 │ собственная Secure + HttpOnly + SameSite cookie
 ▼
Python middleware
 ├── провайдер авторизации ТехПортала
 ├── собственные серверные сессии в Redis
 ├── кэширующий слой Redis
 ├── адаптер заявок ТехПортала
 └── backend-адаптер ESB API
          │
          │ Authorization: Bearer <ESB_BASE_TOKEN>
          ▼
          ESB

Python middleware ── JSON logs в stdout ── Docker ── Vector ── внешнее хранилище
```

Frontend и API следует размещать на одном origin. Предпочтительная схема:

- PWA доступна на `/`;
- внутренний API доступен на `/api`.

Это позволяет использовать `SameSite=Strict` и не создавать зависимость от
междоменных cookies и сложной CORS-конфигурации.

## Авторизация пользователя

ТехПортал используется только как провайдер идентификации пользователя.

Последовательность входа:

1. PWA отправляет логин и пароль в `POST /api/auth/login`.
2. Middleware выполняет штатную авторизацию в ТехПортале с динамическим CSRF.
3. Ответ ТехПортала подтверждает личность пользователя и предоставляет профиль
   и права.
4. Поле `properties.token`, если оно присутствует, игнорируется.
5. Middleware создаёт собственную серверную сессию приложения.
6. Браузеру возвращается только cookie с непрозрачным идентификатором сессии.

На текущем этапе любой пользователь, успешно прошедший авторизацию в
ТехПортале, допускается в PWA. Дополнительная фильтрация по роли, permissions
или `properties.branch` не выполняется.

Cookies или HTTP-сессия ТехПортала не являются пользовательской сессией
приложения и не сохраняются после завершения входа. Если cookie jar технически
нужен между получением `/csrf-token` и отправкой формы входа, он существует
только внутри одной операции авторизации и уничтожается после неё.

Логин, пароль, CSRF-токен и cookies ТехПортала запрещено:

- возвращать frontend;
- сохранять в серверной сессии приложения;
- писать в журналы;
- сохранять в browser storage.

## Cookie приложения

Cookie приложения должна иметь следующие параметры:

```text
HttpOnly
Secure
SameSite=Strict
Path=/
```

Значением cookie является криптографически случайный идентификатор серверной
сессии. Пользовательские токены не хранятся в `localStorage` или
`sessionStorage`.

Абсолютный срок жизни сессии — 12 часов, idle timeout — 8 часов. Каждый
аутентифицированный запрос продлевает idle timeout, но не может продлить сессию
за пределы 12 часов с момента входа. Сессия может быть принудительно отозвана.
Для изменяющих состояние запросов middleware дополнительно проверяет `Origin`
и использует защиту от CSRF.

## Проверка пользовательской сессии

Frontend вызывает `GET /api/auth/session`:

- при запуске приложения;
- после восстановления PWA из фонового состояния;
- после длительного простоя, если это предусмотрено политикой TTL.

Middleware возвращает `401 AUTH_EXPIRED`, если:

- cookie отсутствует;
- серверная сессия не найдена;
- истёк TTL;
- сессия была отозвана;
- учётная запись признана неактивной.

При этом middleware удаляет серверную сессию и отправляет cookie с истёкшим
сроком. Frontend централизованно обрабатывает `401 AUTH_EXPIRED` и открывает
экран входа.

Пароль пользователя не сохраняется и не используется для фоновой
переавторизации. Отдельного REST-метода проверки активности пользователя нет.
Изменения статуса учётной записи в ТехПортале вступают в силу для PWA после
завершения текущей сессии, ручного logout или принудительного отзыва собственной
сессии приложения.

## Доступ backend к ESB API

Backend обращается к ESB с собственным системным Bearer token:

```http
Authorization: Bearer <ESB_BASE_TOKEN>
```

Системный Bearer token:

- хранится только на сервере;
- загружается из `.env`/переменной окружения `ESB_BASE_TOKEN`;
- не связан с `properties.token` пользователя;
- не передаётся в PWA;
- не сохраняется в пользовательской сессии;
- не выводится в журнал.

Ротация системного Bearer token выполняется вручную: значение
`ESB_BASE_TOKEN` заменяется в `.env`, после чего API-контейнер пересоздаётся.
Автоматическое обновление и одновременная поддержка двух токенов на текущем
этапе не реализуются.

Файл `.env` не копируется в Docker image и не включается в репозиторий. Docker
Compose передаёт `ESB_BASE_URL` и `ESB_BASE_TOKEN` приложению как переменные
окружения.

REST-клиент должен иметь настраиваемые тайм-ауты, безопасное журналирование и
единое преобразование ошибок внешней системы во внутренние ошибки приложения.

## Разделение ошибок авторизации

Необходимо различать пользовательскую сессию и авторизацию backend во внешнем
REST API.

### Недействительна пользовательская сессия

- внутренняя сессия удаляется;
- cookie очищается;
- frontend получает `401 AUTH_EXPIRED`;
- PWA открывает экран входа.

### Внешний REST API отклонил системный Bearer token

- пользовательская сессия не удаляется;
- пользователь не отправляется на повторный вход;
- frontend получает безопасную ошибку интеграции, например
  `502 ESB_AUTH_FAILED`;
- полная техническая причина записывается в защищённый серверный журнал;
- событие передаётся в мониторинг.

## Внутренний API текущего этапа

### Авторизация

- `POST /api/auth/login`
- `GET /api/auth/session`
- `POST /api/auth/logout`

### Домофон

- `POST /api/domofon/connect`
- `GET /api/domofon/addresses`
- `POST /api/domofon/create`

### Заявки

- `GET /api/tickets/today`
- `GET /api/tickets/tomorrow`
- `POST /api/tickets/{ticket_id}/completion`

ID исполнителя берётся из серверной сессии. Backend запрашивает страницы
`tickets/get` до первой пустой, передавая московскую календарную дату в формате
`DD.MM.YYYY`. При изменении статуса backend заново получает назначенную
пользователю заявку и отправляет в `tickets/persist` полный набор тегов.
Временные метки UTC преобразуются в `Europe/Moscow`.

Точные структуры запросов и ответов фиксируются до реализации адаптера.
Внутренний API не должен передавать frontend необработанные ответы внешней
системы.

Запрос создания пользователя домофона содержит выбранный адрес, квартиру,
подъезд, ФИО и телефон клиента:

```json
{
  "locid": 123,
  "field_flat": 42,
  "field_podezd": 3,
  "client_name": "Иванов Иван Иванович",
  "phone": "+79990000000"
}
```

Поля `locid`, `field_flat`, `field_podezd` и `client_name` обязательны.
`service_login` и `client_name` — непустые строки. `field_flat` и
`field_podezd` — целые числа. `phone` — необязательная строка: пустое значение
не включается в запрос ESB.
`client_name` и `phone` содержат персональные данные: их нельзя выводить в
технические журналы целиком без необходимости.

Рекомендуемая модель адреса:

```json
{
  "locid": 123,
  "loctext": "ул. Ленина, 5"
}
```

Рекомендуемый формат ошибки:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Не указан номер квартиры",
  "details": {}
}
```

## Обработка ошибок в PWA

Frontend не превращает исключения и неуспешные HTTP-ответы в успешный результат.

Должны отдельно обрабатываться:

- неправильный логин или пароль;
- истёкшая пользовательская сессия;
- ошибка валидации;
- тайм-аут;
- отсутствие сети;
- недоступность внешней системы;
- отказ бизнес-операции;
- ошибка системного Bearer token;
- внутренняя ошибка приложения.

Во время изменяющей состояние операции соответствующая кнопка блокируется,
чтобы предотвратить повторную отправку.

## Redis

Redis используется для двух задач:

- хранение собственных серверных сессий приложения;
- кэширование безопасных read-запросов к внешним REST API.

В production используется один Redis-контейнер с разными номерами логических
БД:

- DB 0 — серверные сессии;
- DB 1 — кэш.

Номера БД задаются конфигурацией. Логические БД разделяют ключи, но используют
общую память, persistence и политику вытеснения. Поэтому требуется контролировать
потребление памяти и выбрать политику, не допускающую незаметного вытеснения
активных сессий. При исчерпании памяти ошибка должна быть обнаружена и
зарегистрирована, а не проигнорирована.

Системный Bearer token, пароли, CSRF-токены и cookies ТехПортала в Redis не
сохраняются.

Кэш работает по схеме cache-aside:

1. backend проверяет значение в Redis;
2. при попадании возвращает кэшированный результат;
3. при промахе вызывает внешний REST API;
4. успешный ответ нормализуется и сохраняется с TTL.

На текущем этапе разрешено кэшировать:

- список адресов домофона;
- результат проверки статуса пользователя, если такой REST endpoint существует
  и его семантика допускает короткий TTL.

Не кэшируются:

- вход и выход пользователя;
- подключение домофона;
- создание пользователя домофона;
- ошибки внешнего API;
- ответы, содержащие секреты или `client_name` и `phone`.

TTL задаётся конфигурацией. Ключ кэша адресов включает версию схемы, но не
`properties.branch`: на текущем этапе branch не влияет на набор данных. При
недоступности Redis-кэша read-запрос
выполняется напрямую через REST API. При недоступности Redis-хранилища сессий
API закрывает доступ и возвращает безопасную ошибку `503`, не переходя на
неявное локальное хранилище.

## Логирование и аудит

Приложение пишет структурированные JSON Lines в `stdout`/`stderr`. Локальные
файлы логов внутри контейнеров не используются. Docker предоставляет поток
контейнерных логов Vector, а дальнейшие sinks Vector настраиваются отдельно от
приложения.

Каждый запрос получает `request_id`. Если корректный `X-Request-ID` пришёл от
доверенного reverse proxy, он может быть продолжен; иначе middleware создаёт
новый идентификатор. `request_id` возвращается в ответе и передаётся во все
внутренние и внешние вызовы.

Минимальные поля записи:

```json
{
  "timestamp": "2026-07-28T12:00:00.000Z",
  "level": "INFO",
  "event": "domofon.create.succeeded",
  "request_id": "01...",
  "user_id": 123,
  "result": "success",
  "http_status": 200,
  "duration_ms": 184
}
```

Обязательные аудит-события:

- `auth.login.succeeded`;
- `auth.login.failed`;
- `auth.logout`;
- `auth.session.expired`;
- `auth.session.revoked`;
- `domofon.connect.succeeded` и `domofon.connect.failed`;
- `domofon.addresses.requested` и `domofon.addresses.failed`;
- `domofon.create.succeeded` и `domofon.create.failed`;
- `esb.auth.failed`;
- ошибки Redis и внешних REST API.

В события действий добавляются подтверждённый `user_id`, результат, HTTP-статус
и длительность. Для неуспешного входа вместо полного логина используется его
необратимый хэш. Идентификатор сессии допускается только в виде необратимого
хэша.

Запрещено журналировать:

- пароль;
- `Authorization`;
- системный Bearer token;
- cookie и идентификатор сессии в открытом виде;
- CSRF-токены;
- полный логин при неуспешной авторизации;
- `client_name`;
- полные тела запросов и ответов без явного безопасного фильтра.

Vector должен выполнять дополнительное удаление запрещённых полей перед
отправкой во внешний sink. В среде разработки Vector читает Docker logs и
отправляет их в console sink. Production sink, срок хранения аудит-логов и
доступ к ним настраиваются позднее на стороне выбранного хранилища.

## Контейнеризация

Развёртывание выполняется в Docker. Минимальный набор сервисов:

- reverse proxy/frontend;
- Python API;
- Redis;
- Vector.

Для локальной разработки и проверки поставляется Docker Compose. Контейнеры
должны запускаться без root, иметь healthcheck, корректно обрабатывать
завершение процесса и получать секреты через переменные окружения или механизм
секретов среды развёртывания.

API предоставляет:

- `/health/live` — процесс работает;
- `/health/ready` — обязательные зависимости готовы.

Недоступность Redis для сессий делает API неготовым. Недоступность Vector не
должна менять результат бизнес-операции, но должна быть видна через мониторинг
инфраструктуры.

## Технологические решения

- frontend: React, TypeScript, Vite, Tailwind CSS, Vite PWA;
- middleware и backend: Python;
- HTTP API middleware: FastAPI;
- модели запросов и ответов: Pydantic;
- серверные сессии и кэш: Redis;
- логирование: структурированный JSON в stdout;
- сбор и маршрутизация логов: Vector;
- развёртывание: Docker и Docker Compose;
- тесты backend: pytest;
- тесты frontend: Vitest и средства тестирования React.

Исходный макет в `examples/figma` не изменяется. Для рабочего приложения он
копируется в `frontend` и очищается от Figma-специфичных и демонстрационных
частей по мере необходимости.

## Требуют уточнения перед интеграцией

- реальные REST endpoints для операций домофона;
- структуры запросов и ответов внешнего API;
- TTL кэша списка адресов;
- persistence и политика памяти единственного production Redis;
- production sink, срок хранения и политика доступа к логам Vector;
- production-адрес и схема публикации frontend/API.
