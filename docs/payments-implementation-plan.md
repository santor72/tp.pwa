# План реализации платёжного терминала

## 1. Назначение

Раздел «Домофоны» заменяется самостоятельным платёжным терминалом для
сотрудников. Платёж не связан с заявками ТехПортала.

Сотрудник последовательно:

1. выбирает адрес или пропускает этот шаг;
2. выбирает разрешённую услугу или товар;
3. вводит данные клиента;
4. проверяет или изменяет сумму;
5. запускает формирование и отправку ссылки на оплату.

Backend находит или создаёт CRM-сущности, формирует платёж средствами
Битрикс24 и сохраняет состояние операции в PostgreSQL. Платёжные системы,
онлайн-касса и отправка SMS должны оставаться на стороне Битрикс24.

## 2. Принятые решения

- Платежи не связываются с заявками ТехПортала.
- Существующий справочник адресов и его Redis-кэш переиспользуются.
- В frontend показываются только товары, разрешённые конфигурацией приложения.
- Лиды не конвертируются и найденные лиды не переводятся на другую стадию.
- Новый лид создаётся только тогда, когда не найден ни подходящий контакт, ни
  подходящий лид.
- Защита от повторного создания сущностей обеспечивается локальной платёжной
  транзакцией и ключом идемпотентности.
- Источник истины для статуса оплаты — Битрикс24, а не frontend и не факт
  открытия клиентом платёжной ссылки.
- Секрет `BX24_WEBHOOK` используется только backend и не передаётся в PWA.

Webhook имеет необходимые scope:

- `crm`;
- `sale`;
- `salescenter`;
- `catalog`;
- `pay_system`.

## 3. Пользовательский сценарий

### 3.1. Шаг «Адрес»

Первым сразу открывается существующий экран выбора адреса.

На экране находятся:

- текстовое поле фильтрации;
- список карточек адресов;
- кнопка «Пропустить адрес».

Выбранный адрес хранится в состоянии формы в виде:

```json
{
  "locid": 123,
  "loctext": "Московская область, г. Чехов, ул. Ленина, д. 10"
}
```

Фильтрация выполняется без учёта регистра по полю `loctext`. При большом
справочнике допускается переход на серверный поиск, но контракт выбранного
адреса не меняется.

Кнопка «Пропустить адрес» сохраняет отсутствие адреса и открывает следующий
шаг. В этом случае поле квартиры далее не показывается.

### 3.2. Шаг «Услуга»

Показывается список услуг и товаров, разрешённых конфигурацией приложения.
Конфигурация задаёт соответствие отображаемого названия и ID товара каталога
Битрикс24.

Пример:

```env
BX24_PAYMENT_PRODUCTS={"Подключение домофона":123,"Оборудование":456}
```

Backend проверяет каждый настроенный товар в Битрикс24 и возвращает frontend
нормализованный список:

```json
[
  {
    "product_id": 123,
    "title": "Подключение домофона",
    "default_amount": "1500.00",
    "currency": "RUB"
  }
]
```

Frontend не получает полный товарный каталог.

### 3.3. Шаг «Клиент»

Поля формы:

- фамилия;
- имя;
- отчество, необязательно;
- телефон;
- квартира/офис, только если был выбран адрес.

Раздельные поля ФИО используются вместо автоматического разбора одной строки.
Номер телефона нормализуется на backend в единый международный формат.

Квартира хранится строкой. Допустимы значения `42`, `12А`, `12/1`, `офис 3`.
Проверка квартиры как целого числа не применяется.

### 3.4. Шаг «Сумма»

Экран показывает:

- выбранную услугу;
- каталожную цену;
- редактируемую итоговую сумму;
- валюту;
- кнопку «Сформировать оплату».

Каталожная цена используется как значение по умолчанию. Сумма передаётся
строкой и обрабатывается backend через `Decimal`, без `float`.

Перед отправкой сотрудник ещё раз видит телефон, услугу и итоговую сумму.

После нажатия кнопки frontend создаёт один ключ идемпотентности и использует
его во всех повторах одного запроса.

### 3.5. Экран результата

Frontend показывает этапы операции:

```text
Ищем клиента…
Создаём платёжный документ…
Добавляем товар…
Формируем ссылку…
Отправляем клиенту…
```

После формирования ссылки доступны:

- итоговый статус;
- короткая платёжная ссылка;
- QR-код;
- кнопка повторной отправки;
- кнопка создания следующей оплаты.

Ошибка SMS не приводит к повторному созданию CRM-сущностей и оплаты.

## 4. Маппинг адреса в лид

Поле `PARENT_ID_1032` является связью с CRM-сущностью «Адресный справочник»
с `entityTypeId=1032`.

Если адрес выбран, при создании нового лида заполняются:

```text
PARENT_ID_1032       = locid
ADDRESS              = полный текст loctext
UF_CRM_1737982006    = квартира/офис
```

Пример:

```json
{
  "PARENT_ID_1032": 123,
  "ADDRESS": "Московская область, г. Чехов, ул. Ленина, д. 10",
  "UF_CRM_1737982006": "42"
}
```

Если адрес пропущен, эти три поля полностью исключаются из запроса. Они не
передаются как `null` или пустые строки.

Поиск лида по адресу выполняется по точному сочетанию:

```json
{
  "PARENT_ID_1032": 123,
  "UF_CRM_1737982006": "42"
}
```

Поле `ADDRESS` при поиске не используется: его текст предназначен для
отображения и может различаться форматированием.

Если существующий лид найден по телефону или адресу, его ФИО, телефон, адрес и
стадия не изменяются. Необязательный e-mail, введённый сотрудником, добавляется
в multi-поле `EMAIL` лида и связанного контакта только если такого адреса там
ещё нет; существующие значения не заменяются.

## 5. Поиск и создание клиента

### 5.1. Нормализация

Перед поиском backend:

- удаляет пробелы и знаки форматирования телефона;
- приводит российский номер к виду `+7XXXXXXXXXX`;
- обрезает пробелы в ФИО и квартире;
- приводит введённый e-mail к нижнему регистру и проверяет его формат;
- сохраняет исходный текст отдельно только там, где он нужен для отображения.

### 5.2. Поиск по телефону

Выполняются два отдельных вызова `crm.duplicate.findbycomm`:

1. `entity_type=CONTACT`, `type=PHONE`;
2. `entity_type=LEAD`, `type=PHONE`.

Раздельные вызовы исключают влияние лимита дублей одной сущности на выдачу
другой сущности.

### 5.3. Алгоритм разрешения клиента

```text
Найден контакт по телефону?
 ├─ найден один → использовать контакт
 ├─ найдено несколько → разрешить неоднозначность
 └─ не найден
      ↓
Найден лид по телефону?
 ├─ найден один → получить связанные контакты
 │    ├─ контакт есть → использовать первичный контакт
 │    └─ контакта нет → создать и добавить контакт к лиду
 ├─ найдено несколько → разрешить неоднозначность
 └─ не найден
      ↓
Выбраны адрес и квартира?
 ├─ да → найти лид по PARENT_ID_1032 + UF_CRM_1737982006
 │    ├─ найден один → использовать или создать его контакт
 │    ├─ найдено несколько → разрешить неоднозначность
 │    └─ не найден → создать новый лид и контакт
 └─ нет → создать новый лид и контакт
```

Если найдено несколько равнозначных сущностей, backend не выбирает первую
автоматически. Он возвращает `409 BX24_CLIENT_AMBIGUOUS`. Frontend показывает
сотруднику безопасный список кандидатов для выбора.

### 5.4. Контакт существующего лида

Для найденного лида:

1. получить связи через `crm.lead.contact.items.get`;
2. использовать первичный контакт, если он есть;
3. если контактов нет, создать контакт;
4. добавить его к лиду через `crm.lead.contact.add`.

Метод `crm.lead.contact.items.set` не используется, поскольку он заменяет весь
список связей и может удалить существующие контакты.

### 5.5. Создание нового лида и контакта

Новый лид получает:

- `TITLE`;
- `NAME`, `SECOND_NAME`, `LAST_NAME`;
- `PHONE`;
- `EMAIL`, если он введён;
- `STATUS_ID` из конфигурации;
- адресные поля из раздела 4, если адрес выбран;
- внешний идентификатор локальной платёжной транзакции, если выбранные методы
  и поля портала позволяют его сохранять.

После создания лида создаётся контакт с теми же ФИО, телефоном и, при наличии,
e-mail, затем контакт
добавляется к лиду. Лид не конвертируется.

У лидов используется `STATUS_ID`; отдельная воронка, аналогичная воронкам
сделок, не создаётся.

## 6. Платёжный документ и оплата

### 6.1. Выбранная модель

Техническим контейнером платежа служит новый CRM-счёт (`entityTypeId=31`),
привязанный к найденному или созданному контакту.

Причины выбора:

- обычный `sale.order` нельзя штатно связать с контактом или лидом через
  `crm.orderentity.add`; поддерживаются только сделка и счёт;
- CRM-счёт поддерживает связь с контактом;
- к нему можно добавить товарную позицию;
- для него поддерживаются `crm.item.payment.*` и публичная платёжная ссылка;
- Битрикс24 создаёт и обслуживает связанный внутренний заказ;
- не требуется создавать сделку или конвертировать лид.

### 6.2. Последовательность вызовов Bitrix24

1. Получить и проверить товар и его цену.
2. Создать CRM-счёт через `crm.item.add` с `entityTypeId=31`.
3. Указать контакт в `contactId`/`contactIds` счёта.
4. Добавить товарную позицию через `crm.item.productrow.add` с
   `ownerType=SI`.
5. Создать оплату через `crm.item.payment.add` с `entityTypeId=31`.
6. Связать товарную позицию с оплатой через
   `crm.item.payment.product.add` (`paymentId`, `rowId`, `quantity=1`).
   При повторной проверке учитывать, что `crm.item.payment.product.list`
   возвращает ID товарной строки в поле `entityId`.
7. Получить URL через `salescenter.payment.getPublicUrl`, передав `id` оплаты.
8. Нормализовать возвращённый QR из base64 в data URL только для отображения в
   PWA.
9. Передать ссылку механизму отправки Bitrix24.

Если сотрудник изменил цену, в товарную позицию передаётся:

- ID товара;
- фактическая цена;
- количество `1`;

Поля `priceExclusive`, `currencyId` и `customized`, отсутствующие во входном
контракте `crm.item.productrow.add`, не отправляются. Каталожная цена и
фактическая цена сохраняются локально раздельно для аудита.

Каталожная и фактическая цены также сохраняются локально.

## 7. Отправка ссылки

Метод `salescenter.payment.getPublicUrl` генерирует полную ссылку, короткую
ссылку и QR-код, но сам не отправляет SMS.

Целевая схема отправки на стороне Битрикс24:

1. backend получает короткую ссылку;
2. записывает её в предназначенное для этого поле CRM-счёта;
3. переводит счёт в согласованное состояние или устанавливает управляющий
   признак;
4. робот Битрикс24 отправляет SMS через настроенного провайдера;
5. результат отправки отражается в локальной транзакции, если Bitrix24
   предоставляет пригодное событие или callback.

До реализации отправки необходимо провести отдельную интеграционную проверку:

- определить поле счёта для ссылки;
- определить запускающую стадию или флаг;
- проверить шаблон SMS;
- проверить повторную отправку;
- определить способ получения статуса доставки.

Даже при ошибке отправки сформированные короткая ссылка и QR-код остаются
доступны сотруднику.

## 9. Состояния транзакции

```text
draft
resolving_client
client_resolved
invoice_created
product_added
payment_created
link_created
send_queued
sent
paid
send_failed
failed
expired
canceled
```

Каждый успешный внешний шаг фиксируется в PostgreSQL до перехода к следующему.
Повтор операции продолжается с последнего подтверждённого шага.

Статус `failed` хранит этап и тип ошибки. Если внешняя сущность уже создана,
повтор не создаёт её заново.

После исчерпания лимита повторов `failed` — финальное состояние для worker.
Возобновление такой операции выполняется только отдельным согласованным
административным действием, а не неявным повторным запуском процесса.

## 10. Идемпотентность и восстановление

- Frontend создаёт `idempotency_key` один раз на одну попытку оплаты.
- В PostgreSQL действует уникальное ограничение на этот ключ.
- Повторный `POST` с тем же ключом возвращает существующую транзакцию.
- После каждого создания внешней сущности её ID сразу сохраняется.
- CRM-счёт получает внешний идентификатор на основе UUID транзакции, если это
  поддерживается выбранным полем.
- Перед повторным созданием после неопределённого ответа backend пытается найти
  уже созданную сущность по внешнему идентификатору.
- Повторная отправка SMS не создаёт новый счёт и платёж.
- Перед автоматическим повтором триггера отправки backend читает CRM-счёт и не
  повторяет write, если поле ссылки и триггер уже имеют нужные значения.
  Явное действие сотрудника «Отправить повторно» выполняет новый trigger-write.
- Создание новой оплаты для той же услуги является отдельным явным действием и
  получает новый ключ идемпотентности.

## 11. Отслеживание статуса оплаты

Основной источник — событие Bitrix24 `OnPaymentEntitySaved`.

Endpoint проверяет `auth[application_token]` из тела события (или внутренний
заголовок `X-Bitrix-Token`) через constant-time сравнение с
`BX24_PAYMENT_WEBHOOK_TOKEN`. Секрет не передаётся в query string, чтобы он не
попадал в access logs reverse proxy.

Обработчик:

1. получает ID платежа;
2. находит локальную транзакцию;
3. повторно читает оплату из Bitrix24;
4. проверяет фактический признак оплаты;
5. идемпотентно переводит транзакцию в `paid`;
6. создаёт записи в таймлайне, если они ещё не создавались.

Резервный worker периодически проверяет незавершённые операции в состояниях
`link_created`, `send_queued`, `sent` и `send_failed`. Проверка прекращается для
`paid`, `expired` и `canceled`.

По истечении TTL операция с уже созданной оплатой сначала повторно читается в
Bitrix24. В `expired` переводится только подтверждённо неоплаченная операция;
наличие локального дедлайна само по себе не может затереть фактическую оплату.

## 12. Таймлайн CRM

После формирования ссылки создаётся комментарий:

- в контакте;
- в лиде, если операция связана с лидом.

Пример безопасного текста:

```text
Сформирована оплата №1234
Услуга: Подключение домофона
Сумма: 1 500 ₽
Статус: ссылка передана клиенту
Операция ТехПортала: <UUID>
```

Публичная платёжная ссылка в комментарий не включается.

После подтверждения оплаты создаётся отдельный комментарий:

```text
Оплата №1234 подтверждена
Сумма: 1 500 ₽
```

Успешная отправка фиксируется завершённым делом. Если SMS не отправлено,
создаётся открытое дело «Повторно отправить ссылку клиенту».

Одно и то же дело по возможности связывается и с лидом, и с контактом через
bindings, вместо создания дубликатов.

## 13. Внутренний API

Предлагаемые маршруты:

```text
GET  /api/payments/addresses
GET  /api/payments/products
POST /api/payments
GET  /api/payments/{transaction_id}
POST /api/payments/{transaction_id}/client-selection
POST /api/payments/{transaction_id}/resend
GET  /api/payments/recent
POST /api/webhooks/bitrix24/payments
```

`POST /api/payments` принимает:

```json
{
  "idempotency_key": "UUID",
  "address": {
    "locid": 123,
    "loctext": "Полный адрес"
  },
  "apartment": "42",
  "product_id": 123,
  "first_name": "Иван",
  "second_name": "Иванович",
  "last_name": "Иванов",
  "phone": "+79991234567",
  "amount": "1500.00"
}
```

При пропуске адреса поля `address` и `apartment` отсутствуют.

Ответ `202 Accepted` содержит ID локальной транзакции и текущее состояние.

## 14. Конфигурация

Минимальный набор:

```text
BX24_WEBHOOK
BX24_PAYMENT_PRODUCTS
BX24_PRICE_GROUP_ID
BX24_NEW_LEAD_STATUS_ID

```

Точные `BX24_PAYMENT_LINK_FIELD` и `BX24_PAYMENT_SEND_TRIGGER` определяются
после проверки робота отправки SMS.

Backend валидирует формат конфигурации при старте, а доступность разрешённых
товаров — при первом обращении с кэшированием результата. Пустой webhook или
словарь товаров делает платёжные endpoints недоступными с безопасным кодом
`503 PAYMENTS_NOT_CONFIGURED`, не мешая авторизации и работе с заявками.

## 15. Права и безопасность

- Capability `domofon` заменяется на `payments`.
- Доступ к разделу и каждому изменяющему endpoint проверяется backend.
- Право `permissions.tickets.execution` является явным условием доступа
  сотрудника к терминалу.
- Применяется существующая серверная сессия, CSRF-проверка и SameSite cookie.
- Вводятся минимальная и максимальная суммы.
- Возможность менять цену управляется отдельным разрешением.
- В аудит-логах сохраняются ID операции, сотрудник, товар и сумма, но не полный
  телефон и не платёжная ссылка.
- `BX24_WEBHOOK` никогда не возвращается frontend и не выводится в лог.

Webhook действует от имени одного пользователя Битрикс24. Реальный сотрудник
ТехПортала сохраняется в PostgreSQL и указывается в безопасном тексте
комментария. Если нужна персональная атрибуция внутри Битрикс24, потребуется
сопоставление пользователей и дополнительный scope `user`.

## 16. Компоненты backend

Новые компоненты:

```text
Bitrix24Client
PaymentService
PaymentRepository
PaymentWorker
PaymentStatusHandler
PaymentProductCatalog
```

Ответственность:

- `Bitrix24Client` — HTTP, тайм-ауты, retry чтения, нормализация ошибок и
  безопасное логирование;
- `PaymentProductCatalog` — конфигурация разрешённых товаров и цены;
- `PaymentService` — оркестрация шагов и идемпотентность;
- `PaymentRepository` — транзакции и история событий PostgreSQL;
- `PaymentWorker` — продолжение незавершённых операций и polling;
- `PaymentStatusHandler` — события оплаты Bitrix24.

## 18. Критерии готовности

Сценарий считается готовым, когда:

- повторное нажатие не создаёт дубли;
- поиск клиента выполняется в согласованном порядке;
- существующие лиды не конвертируются и не изменяются;
- адрес записывается только при его выборе;
- товар и базовая цена загружаются из Битрикс24;
- изменение цены фиксируется в аудите;
- счёт связан с контактом;
- ссылка и QR создаются средствами Битрикс24;
- сбой SMS не уничтожает и не дублирует оплату;
- статус `paid` устанавливается только после подтверждения Bitrix24;
- в контакте и, при наличии, в лиде есть записи о формировании и оплате;
- все внешние ID и состояния восстановления сохранены в PostgreSQL;
- секреты и платёжные ссылки отсутствуют в логах и ответах, где они не нужны.
