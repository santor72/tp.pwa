# Архитектура мессенджеров

## Статус решения

Решение принято. Telegram реализуется первым мессенджером, но
доменная модель, хранение и прикладные сервисы не должны зависеть от
Telegram. Следующие мессенджеры подключаются как новые адаптеры.

## Цели

- добавить Telegram-бота как второй frontend к существующему backend;
- не дублировать логику заявок, Домофона, прав и аудита;
- связывать мессенджер с уже авторизованным в PWA пользователем;
- хранить постоянные идентичности и привязки в PostgreSQL;
- допускать к боту только участников разрешённых Telegram-групп;
- оставить возможность добавлять другие мессенджеры без изменения
  бизнес-логики.

## Общая схема

```text
PWA (React) ── HTTP + cookie ─┐
                            ├── прикладные сервисы ── ТехПортал / ESB
Telegram ── aiogram/polling ─┘              │
                                      ├── PostgreSQL
                                      └── Redis
```

PWA и Telegram являются адаптерами доставки. Они преобразуют свою
аутентификацию в общий контекст исполнителя `Actor`. Прикладные сервисы
не должны зависеть от HTTP cookie, CSRF, `telegram_id`, `Message` или `CallbackQuery`.

```text
Actor
  user_id                 # внутренний UUID
  techportal_user_id      # ID исполнителя в ТехПортале
  channel                 # pwa | messenger
  provider                # null | telegram | другой провайдер
  external_identity_id    # null или ID привязки
  permissions             # актуальные точечные права ТехПортала
  role                    # admin | manager | user, вычисляется из status
```

## Границы сервисов

### API

- авторизует через ТехПортал и ведёт PWA-сессии;
- при успешном входе делает upsert пользователя в PostgreSQL;
- создаёт, показывает и отзывает привязки мессенджеров;
- генерирует deep-link без доступа к `TELEGRAM_BOT_TOKEN`.

### `telegram-bot`

- работает отдельным контейнером на aiogram;
- на первом этапе получает события через long polling;
- проверяет доступ до вызова любого бизнес-сценария;
- потребляет одноразовые токены и создаёт привязки;
- вызывает общие прикладные сервисы без обратных HTTP-запросов в API;
- хранит FSM-состояния в Redis.

При long polling допустим только один экземпляр `telegram-bot`. Масштабирование и
переход на webhook являются отдельным этапом.

## Постоянная модель

### `users`

| Поле | Назначение |
|---|---|
| `id UUID PK` | Внутренний стабильный ID |
| `techportal_user_id TEXT UNIQUE` | Внешний ID ТехПортала |
| `email TEXT` | Актуальный email профиля |
| `first_name TEXT NULL` | Отображаемое имя |
| `status TEXT NULL` | Последний известный статус ТехПортала |
| `permissions JSONB` | Последние известные permissions |
| `created_at`, `updated_at`, `last_login_at` | Аудит профиля |

Профиль обновляется при каждом успешном входе в PWA. PostgreSQL не хранит пароль,
cookie, CSRF или токены ТехПортала.

Актуальность `status` и `permissions` ограничена последним входом в PWA, как и в текущей
архитектуре: отдельного endpoint проверки активности нет. Постоянным оперативным
ограничением Telegram служит членство в `TG_ACCESS_GROUPS`; принадлежность каждой заявки
повторно проверяется в ТехПортале. Если появится надёжный endpoint активности/прав, его
проверка добавляется в общую авторизацию `Actor`, а не в Telegram handlers.

`role` не хранится отдельным полем: оно детерминированно вычисляется из `status` при
построении `Actor`. Статусы `admin` и `manager` образуют одноимённые уровни; любой
другой статус, в том числе пустой, соответствует базовому уровню `user`.

## Capabilities PWA

Ответы `POST /api/auth/login` и `GET /api/auth/session` содержат вычисленный объект
`capabilities`. Интерфейс использует только его для показа разделов, а API повторяет
проверку перед выполнением операции:

| Capability | Правило |
|---|---|
| `domofon` | `permissions.client.create === true` |
| `messenger_settings` | роль `admin` или `MESSENGER_SHOW=true` |
| `all_tickets` | роль `admin` или `manager` |

`MESSENGER_SHOW` по умолчанию равен `false`. На время тестирования также поддерживается
историческое написание переменной `MESSENDGER_SHOW`, но для новых конфигураций следует
использовать только `MESSENGER_SHOW`.

Режим `GET /api/tickets/{day}?scope=all` доступен только с `all_tickets`; он возвращает
заявки только для чтения. Изменение отметки выполнения всегда повторно проверяет, что
заявка назначена текущему исполнителю.

### `messenger_identities`

| Поле | Назначение |
|---|---|
| `id UUID PK` | ID привязки |
| `user_id UUID FK` | Внутренний пользователь |
| `provider TEXT` | `telegram` или будущий провайдер |
| `provider_user_id TEXT` | ID пользователя у провайдера |
| `username`, `display_name` | Необязательные метаданные |
| `linked_at`, `revoked_at` | Жизненный цикл привязки |

Ограничения:

- один `provider_user_id` не может быть привязан к двум пользователям одного
  провайдера;
- у одного внутреннего пользователя может быть только одна активная привязка
  каждого провайдера;
- повторная привязка требует явного отзыва прежней.

Ограничения активных связей реализуются частичными уникальными индексами
по строкам, где `revoked_at IS NULL`.

### `messenger_link_tokens`

| Поле | Назначение |
|---|---|
| `id UUID PK` | ID попытки привязки |
| `user_id UUID FK` | Инициатор из PWA |
| `provider TEXT` | Целевой мессенджер |
| `token_hash TEXT UNIQUE` | SHA-256 от случайного токена |
| `expires_at` | Короткий срок действия |
| `consumed_at` | `NULL` до успешной привязки |
| `invalidated_at` | Отмена новой ссылкой или отзывом привязки |
| `created_at` | Аудит создания |

Исходный токен нигде не хранится. Поглощение токена и создание привязки
выполняются в одной транзакции с блокировкой строки. Токен можно поглотить только
один раз, только до `expires_at` и при `invalidated_at IS NULL`. Создание новой ссылки
инвалидирует прежние неиспользованные токены того же пользователя и провайдера. Отзыв
привязки также инвалидирует все её ожидающие токены.

## Привязка Telegram

1. Специалист входит в PWA через ТехПортал.
2. PWA отправляет CSRF-защищённый `POST /api/messenger-links/telegram`.
3. API создаёт одноразовый токен и возвращает `deep_link` и `expires_at`.
4. Telegram передаёт боту `/start <token>`.
5. Бот до обработки токена проверяет членство Telegram-пользователя в
   `TG_ACCESS_GROUPS`.
6. При разрешённом доступе бот атомарно поглощает токен и создаёт привязку.
7. Все последующие Telegram-события проходят повторную проверку групп через
   кэш, а затем поиск активной привязки.

В первой версии deep-link считается bearer-секретом. Риск его пересылки снижается
криптографической случайностью, одноразовостью и TTL. Двустороннее подтверждение
в PWA может быть добавлено позже без изменения модели.

## Доступ по Telegram-группам

`TG_ACCESS_GROUPS` содержит упорядоченный список числовых Telegram chat ID. Достаточно
членства в любой группе. Проверка идёт по порядку и останавливается на первом
успешном совпадении.

Разрешены статусы:

- `creator`;
- `administrator`;
- `member`;
- `restricted` только при `is_member=true`.

`left` и `kicked` запрещены. Для надёжной проверки боту выдаются права администратора
во всех группах из списка.

Проверка применяется к каждому типу update: командам, сообщениям и callback-кнопкам. Для
непривязанного, но разрешённого пользователя допустим только экран инструкции по
привязке. Непрошедшие проверку групп не получают бизнес-данные; первая версия
молча игнорирует их update.

Ключ кэша:

```text
telegram:access:v1:<groups-config-hash>:<telegram-user-id>
```

В кэш записываются как разрешение, так и отказ. Хэш каноничной строки
`TG_ACCESS_GROUPS` включается в ключ, поэтому изменение списка не требует очистки Redis.
Ошибки Telegram API не кэшируются. При невозможности подтвердить членство доступ
закрывается (fail closed), а бизнес-операция не выполняется.

## Конфигурация

```dotenv
DATABASE_URL=postgresql+asyncpg://techportal:change-me@postgres:5432/techportal
TELEGRAM_BOT_TOKEN=
TELEGRAM_BOT_USERNAME=
TG_ACCESS_GROUPS=-1001111111111,-1002222222222
TG_ACCESS_CACHE_TTL_SECONDS=300
TG_LINK_TOKEN_TTL_SECONDS=600
REDIS_BOT_DB=2
HTTPS_PROXY=http://proxy.example:3128
```

- `TELEGRAM_BOT_TOKEN` передаётся только `telegram-bot`;
- API получает `TELEGRAM_BOT_USERNAME`, но не получает bot token;
- `TG_ACCESS_GROUPS` передаётся только `telegram-bot`;
- `TG_ACCESS_CACHE_TTL_SECONDS` определяет максимальную задержку после изменения
  членства;
- `REDIS_BOT_DB` отделяет Telegram access/FSM от PWA-сессий и общего кэша.
- `HTTPS_PROXY` обязателен для `telegram-bot` при long polling и берётся из `.env`;
  bot composition root явно передаёт его в HTTP-сессию aiogram, чтобы через прокси
  выполнялись все обращения к Telegram API, включая удаление webhook и polling;
  значение прокси не журналируется и не передаётся API/frontend.

В production секреты могут поступать из secret manager через переменные окружения; файл `.env`
не включается в image и репозиторий.

## Внутренний API для PWA

- `GET /api/messenger-links` — список активных привязок;
- `POST /api/messenger-links/telegram` — создать одноразовую deep-link;
- `DELETE /api/messenger-links/telegram` — отозвать Telegram-привязку.

Все методы требуют PWA-сессию. `POST` и `DELETE` дополнительно требуют Origin и CSRF.

## Ошибки и аудит

Должны различаться:

- неверный, истёкший или уже использованный link token;
- Telegram ID уже связан с другим пользователем;
- у пользователя уже есть активная Telegram-привязка;
- нет членства в разрешённых группах;
- Telegram API временно недоступен;
- PostgreSQL или Redis недоступны;
- ошибка внешней бизнес-системы.

Аудит-события содержат внутренний `user_id`, `channel`, `provider`, результат и код ошибки.
`TELEGRAM_BOT_TOKEN`, link token, пароли, cookie, CSRF и полные тела update не журналируются.

## Миграции и запуск

- ORM: SQLAlchemy 2 async;
- драйвер: `asyncpg`;
- миграции: Alembic;
- миграции запускаются отдельно до запуска/обновления приложения;
- API и `telegram-bot` не запускают миграции конкурентно;
- readiness API и бота учитывает доступность PostgreSQL;
- для long polling не открывается публичный порт бота.
- `telegram-bot` запускается только с настроенным `HTTPS_PROXY`; отсутствие или
  некорректное значение считается ошибкой конфигурации до начала polling.

## Отложенные решения

- webhook и горизонтальное масштабирование;
- двустороннее подтверждение deep-link в PWA;
- несколько активных учётных записей одного провайдера на одного
  специалиста;
- push-уведомления и фоновые рассылки;
- конкретный следующий мессенджер.
