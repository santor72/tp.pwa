# Реализация экранов заявок «Сегодня» и «Завтра»

## Назначение документа

Документ описывает фактическую реализацию заявок на всех уровнях приложения:

- интеграцию backend с API ТехПортала;
- внутренний API PWA;
- преобразование и защиту данных;
- интерфейс экранов «Сегодня» и «Завтра»;
- изменение статуса заявки;
- тестирование и эксплуатацию.

Исходные бизнес-требования находятся в `docs/tt.md`. Этот документ отражает
реализованное состояние с учётом уточнений, появившихся во время разработки.

## Общая схема

```text
React PWA
  │
  │ Cookie серверной сессии + X-CSRF-Token для изменений
  ▼
FastAPI
  ├── получает ID пользователя из Redis-сессии
  ├── рассчитывает дату в Europe/Moscow
  ├── нормализует заявки и комментарии
  ├── проверяет принадлежность заявки пользователю
  └── кэширует справочник пользователей в Redis
  │
  │ Authorization: Bearer <TP_BASE_TOKEN>
  ▼
API ТехПортала
  ├── POST tickets/get
  ├── GET techportal-user/list
  └── POST tickets/persist
```

Frontend никогда не получает системный `TP_BASE_TOKEN` и не определяет ID
исполнителя самостоятельно.

## Конфигурация

Используются следующие переменные окружения:

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `TP_BASE_URL` | Полный базовый путь внешнего API, например `https://tp.point.online/api/ext` | `https://tp.point.online` |
| `TP_BASE_TOKEN` | Системный Bearer-токен для заявок | пусто |
| `TP_API_TIMEOUT_SECONDS` | Тайм-аут запросов к API заявок | `20` |
| `TP_TICKETS_MAX_PAGES` | Максимум страниц `tickets/get` за один запрос PWA | `100` |
| `TP_USERS_CACHE_TTL_SECONDS` | TTL справочника пользователей в Redis | `300` |

`TP_BASE_URL` содержит путь внешнего API. Endpoints заявок добавляются к этому
значению:

```text
<TP_BASE_URL>/tickets/get
<TP_BASE_URL>/techportal-user/list
<TP_BASE_URL>/tickets/persist
```

Авторизация пользователя использует тот же домен, но не путь `/api/ext`.
Backend извлекает из `TP_BASE_URL` только origin и вызывает:

```text
<origin>/csrf-token
<origin>/api/techportal-user/login
```

Если URL или токен заявок не настроены, backend возвращает
`503 TECHPORTAL_NOT_CONFIGURED`.

## Пользователь и серверная сессия

При успешной авторизации профиль ТехПортала преобразуется во внутренний
`UserProfile`. Поле `id` сохраняется внутри `SessionData` в Redis.

Для каждого запроса заявок backend:

1. получает серверную сессию по HttpOnly cookie;
2. берёт `session.user.id`;
3. передаёт этот ID в `masterIds`;
4. дополнительно отбрасывает все ответы, в которых ID отсутствует в `masters`.

Двойная фильтрация не позволяет показать чужую заявку даже при некорректной
работе фильтра внешнего API.

## Получение заявок из ТехПортала

Используется `POST tickets/get`. Backend последовательно запрашивает страницы от
`page: 0` до первой пустой страницы. Повторяющаяся страница или
`TP_TICKETS_MAX_PAGES` останавливают загрузку и записываются в аудит-лог.
Поле `closedFrom` намеренно не передаётся: в ТехПортале значение `"-"`
исключает уже закрытые заявки. Их показ управляется переключателем «Закрытые»
в PWA.

Пример тела запроса:

```json
{
  "page": 0,
  "filters": {
    "and": [
      {
        "tags": {},
        "createdBy": [],
        "masterIds": [87],
        "scheduledTo": "30.07.2026",
        "scheduledFrom": "30.07.2026"
      }
    ]
  }
}
```

Календарная дата рассчитывается на backend:

- `today` — текущая дата в `Europe/Moscow`;
- `tomorrow` — следующая календарная дата в `Europe/Moscow`;
- формат внешнего запроса — `DD.MM.YYYY`.

Значения `scheduledDate` и `history[].createdAt` принимаются как UTC и
преобразуются в `Europe/Moscow`.

## Нормализация заявки

Backend не передаёт frontend необработанный объект ТехПортала. Внутренняя
модель заявки:

```json
{
  "id": 32412,
  "address": "СНТ Волга, участок 96, дом 12, кв. 34",
  "client_phone": "79254553958",
  "client_name": "Денис Денис",
  "description": "Описание работ",
  "scheduled_at": "2026-07-30T12:00:00+03:00",
  "kind": "connection",
  "completed": false,
  "tags": {
    "Новое подключение": {}
  },
  "comments": [
    {
      "created_at": "2026-07-30T11:13:21.930000+03:00",
      "author": "Константин",
      "text": "Работы согласованы"
    }
  ]
}
```

### Тип и состояние

Тип определяется по ключам `tags`:

- есть `Новое подключение` — `kind: "connection"`;
- тега нет — `kind: "repair"`.

Состояние определяется аналогично:

- есть `Работы произведены` — `completed: true`;
- тега нет — `completed: false`.

### Адрес

Адрес собирается из `address` в следующем порядке:

1. `externalAddress`;
2. `дом {house}`, если `house` не `null` и не пустая строка;
3. `кв. {apartment}`, если `apartment` не `null` и не пустая строка.

Части соединяются запятыми. Пробелы по краям значений удаляются.

Примеры:

```text
СНТ Волга, участок 96
СНТ Волга, участок 96, дом 12
СНТ Волга, участок 96, дом 12, кв. 34
```

### Телефон

Используется:

1. `clientPhone`;
2. первый элемент `phones`, если `clientPhone` отсутствует;
3. пустая строка, если телефон не найден.

### Сортировка

После нормализации заявки сортируются по `scheduled_at` по возрастанию.
Заявки без назначенного времени располагаются в конце списка.

## Комментарии

Комментарии извлекаются из `history`:

1. перебираются все элементы `history`;
2. внутри каждого элемента перебираются `changes`;
3. выбираются изменения с `key == "comments"`;
4. дата берётся из `history[].createdAt`;
5. ID автора берётся из `history[].techportalUser`;
6. текст берётся из `changes[].value`.

Имена авторов загружаются через `GET techportal-user/list`. В Redis хранится
словарь:

```json
{
  "3": "Константин",
  "4": "Архипов Андрей"
}
```

Ключ кэша — `techportal:users:v1`, TTL задаётся
`TP_USERS_CACHE_TTL_SECONDS`. Ошибка Redis не блокирует запрос: справочник
загружается напрямую из ТехПортала.

Если пользователь не найден, отображается `Пользователь #<id>`. Комментарии
сортируются по времени по возрастанию. Значения, являющиеся URL, frontend
показывает как внешние ссылки.

## Внутренний API PWA

Все endpoints требуют действующую серверную сессию.

### Получить заявки на сегодня

```http
GET /api/tickets/today
```

Ответ — массив нормализованных заявок.

### Получить заявки на завтра

```http
GET /api/tickets/tomorrow
```

Ответ имеет тот же формат.

### Изменить отметку исполнения

```http
POST /api/tickets/{ticket_id}/completion
Content-Type: application/json
X-CSRF-Token: <csrf_token>
```

Тело:

```json
{
  "day": "today",
  "completed": true
}
```

`day` принимает `today` или `tomorrow`. Ответ — обновлённая нормализованная
заявка.

Frontend не отправляет набор тегов. Это предотвращает перезапись заявки
устаревшими данными из браузера.

## Изменение статуса

Последовательность изменения статуса:

1. backend повторно вызывает `tickets/get` для указанного дня и пользователя;
2. находит заявку одновременно по `id` и наличию пользователя в `masters`;
3. если заявка не найдена, возвращает `404 TICKET_NOT_FOUND`;
4. копирует полный актуальный словарь `tags`;
5. при исполнении добавляет `"Работы произведены": {}`;
6. при возврате в работу удаляет ключ `Работы произведены`;
7. при закрытии ремонта получает заявку по `id`, добавляет обязательный `comments` и
   отправляет полный словарь заявки в `POST tickets/persist` вместе с обновлёнными тегами;
8. объединяет ответ persist с исходной полной заявкой;
9. возвращает frontend обновлённую нормализованную заявку.

Внешнее тело:

```json
{
  "ticket": {
    "id": 32412,
    "tags": {
      "Солнечногорск": {},
      "Новое подключение": {},
      "Работы произведены": {}
    }
  }
}
```

`tickets/persist` может возвращать как полный, так и сокращённый объект.
Объединение выполняется только по явно присутствующим в ответе полям и
сохраняет типизированные вложенные элементы `history`. Это предотвращает
обнуление карточки и ошибки обработки комментариев после долгого нажатия.

## Ошибки интеграции

| Статус | Код | Условие |
|---|---|---|
| `401` | `AUTH_EXPIRED` | Нет или истекла пользовательская сессия |
| `403` | `CSRF_INVALID` | Некорректный CSRF при изменении |
| `404` | `TICKET_NOT_FOUND` | Заявка не назначена пользователю или отсутствует на выбранный день |
| `502` | `TECHPORTAL_AUTH_FAILED` | Внешний API отклонил системный Bearer-токен |
| `502` | `TECHPORTAL_CALL_FAILED` | Внешний API вернул ошибочный HTTP-статус |
| `502` | `TECHPORTAL_RESPONSE_INVALID` | Ответ не соответствует ожидаемой схеме |
| `503` | `TECHPORTAL_NOT_CONFIGURED` | Не задан URL или токен |
| `503` | `SERVICE_UNAVAILABLE` | Сетевая ошибка или недоступность ТехПортала |

Внешний `401/403` не удаляет пользовательскую сессию PWA.

## Аудит-события

Backend пишет структурированные события:

```text
tickets.list.succeeded
tickets.list.failed
tickets.completion.changed
tickets.completion.failed
techportal.request.unavailable
techportal.request.failed
techportal.auth.failed
```

В аудит включаются `request_id`, `user_id`, выбранный день, ID заявки,
результат и код ошибки. Bearer-токен, содержимое комментариев, телефон и имя
клиента в журнал не записываются.

## Frontend

### Навигация

Нижнее меню содержит:

- «Сегодня»;
- «Завтра»;
- «Домофон».

При переключении дня вызывается соответствующий endpoint. Для каждого экрана
предусмотрены состояния загрузки, пустого результата, ошибки и ручного
обновления.

### Карточка

Карточка занимает всю ширину области приложения и показывает:

- тип заявки;
- состояние;
- адрес;
- назначенное время в `Europe/Moscow`;
- телефон как ссылку `tel:`.

Цветовая кодировка:

- неисполненное новое подключение — белый фон;
- неисполненный ремонт — слабо-розовый радиальный градиент;
- исполненная заявка любого типа — слабо-зелёный радиальный градиент.

### Взаимодействие

- короткий тап открывает подробности;
- долгое нажатие длительностью 600 мс переключает исполнение;
- после долгого нажатия событие короткого тапа подавляется;
- на время запроса карточка блокируется и показывает `Изменение…`;
- при успехе в списке заменяется только изменённая заявка;
- при ошибке исходная карточка сохраняется и показывается сообщение;
- в подробностях доступна отдельная кнопка изменения состояния.

### Подробности

Экран подробностей показывает:

- номер и назначенное время заявки;
- тип и состояние;
- имя клиента;
- полный адрес;
- телефон;
- описание;
- ленту комментариев с датой, автором и текстом.

## Принятые ограничения

- загрузка заявок ограничена `TP_TICKETS_MAX_PAGES` страницами за один запрос;
- список заявок не кэшируется;
- справочник пользователей кэшируется на 5 минут по умолчанию;
- при закрытии ремонта комментарий обязателен и сохраняется вместе с заявкой;
- экран подробностей использует данные, уже полученные в списке;
- время и календарные даты интерфейса всегда отображаются в
  `Europe/Moscow`.
