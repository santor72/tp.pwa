# Исполняемый план разработки платёжного терминала

## Цель Goal

Заменить раздел «Домофоны» на устойчивый платёжный терминал: сотрудник выбирает
адрес (или пропускает), товар, клиента и сумму; backend идемпотентно находит или
создаёт CRM-сущности, создаёт в Битрикс24 счёт, товарную позицию и оплату,
получает платёжную ссылку, ставит её в очередь отправки средствами Битрикс24,
сохраняет весь прогресс в PostgreSQL и подтверждает оплату по данным Битрикс24.

Архитектурные требования и бизнес-правила находятся в
[`payments-implementation-plan.md`](payments-implementation-plan.md). Этот
документ задаёт порядок исполнения, границы этапов и проверки.

## Правила выполнения Goal

- Выполнять этапы последовательно; следующий этап начинается после прохождения
  проверок предыдущего.
- Не создавать реальные CRM-сущности и платежи во время автоматических тестов.
- Все вызовы Bitrix24 в unit/integration-тестах подменять контролируемым fake
  transport.
- Ручной smoke-тест с реальным Bitrix24 выполнять только на согласованных
  тестовых контакте, товаре и сумме.
- Не выводить `BX24_WEBHOOK`, телефоны и полные платёжные ссылки в логах,
  исключениях и test snapshots.
- Сохранять существующие несвязанные изменения в рабочем дереве.
- Не оставлять старый и новый пользовательские сценарии одновременно: после
  переключения раздел должен называться «Оплата» и использовать новые API.
- Каждый внешний write-шаг должен быть повторяемым без создания дублей.
- Если внешняя настройка SMS ещё не подготовлена, завершить программную часть с
  явно работающим состоянием `send_queued`/`send_failed`, QR и короткой ссылкой;
  не имитировать успешную отправку.

## Зафиксированные допущения для автономного выполнения

- Переходная capability `payments` использует то же серверное право
  `permissions.client.create`, которое ранее открывало раздел «Домофоны».
  Проверка остаётся на backend. Выделение отдельного права — отдельная задача
  после согласования модели прав ТехПортала.
- Адреса продолжает предоставлять ESB; контракт элемента — `locid`, `loctext`.
- При выбранном адресе квартира обязательна, но является строкой.
- В новый лид записываются:

  ```text
  PARENT_ID_1032       = locid
  ADDRESS              = loctext
  UF_CRM_1737982006    = квартира
  ```

- При пропуске адреса эти поля не передаются.
- Найденный лид не конвертируется, не переводится на другую стадию и не
  обновляется данными формы.
- Платёжным контейнером является CRM-счёт `entityTypeId=31`, связанный с
  контактом.
- Валюта MVP — `RUB`, количество выбранного товара — `1`.
- Создание операции асинхронное: `POST /api/payments` создаёт локальную запись
  и возвращает `202`, дальнейшие шаги выполняет worker.

4. Нормализовать ответы Bitrix24 и ошибки в безопасные внутренние коды:
   `BX24_NOT_CONFIGURED`, `BX24_AUTH_FAILED`, `BX24_ACCESS_DENIED`,

9. Не подменять недоступную цену значением `0`; товар исключать либо возвращать
   `503 PAYMENTS_CATALOG_UNAVAILABLE`.

### Тесты

- успешный ответ и Bitrix envelope error;
- timeout, `401/403`, `429` с backoff, `5xx`;
- секрет и PII отсутствуют в сообщении ошибки;
- неизвестный/неактивный товар;
- несколько типов цен и выбор `BX24_PRICE_GROUP_ID`;
- Redis hit/miss и истечение TTL;
- frontend-список не содержит посторонних товаров каталога.

### Готово, когда

- каталог формируется только из конфигурации;
- клиент не повторяет неизвестный write-запрос автоматически;
- все технические ошибки имеют стабильные безопасные коды.

- товар добавлен, оплата не создана;
- оплата создана, ссылка не получена;
- ссылка создана, отправка не сработала;
- повтор каждого состояния;
- повторная отправка;
- каталожная цена и изменённая цена;
- комментарий создан только в контакте;
- комментарий создан в контакте и лиде;
- повторный callback не дублирует комментарии и activity.

### Готово, когда

- каждый частичный сбой возобновляется с последнего сохранённого шага;
- два параллельных запуска одной операции не создают дубли;
- короткая ссылка и QR доступны независимо от результата SMS.

4. Обрабатывать `OnPaymentEntitySaved`: по ID повторно читать платёж и доверять

7. По TTL переводить только неоплаченные операции в `expired`; не удалять
   внешние документы автоматически.
8. Добавить graceful shutdown и структурированные безопасные audit events.
9. Добавить сервис `payment-worker` в Compose с зависимостью от migration и
   PostgreSQL; секреты передать через environment.

### Тесты

- два worker не берут одну запись;
- backoff и предел повторов;
- webhook до сохранения локального `payment_id` обрабатывается повторно;
- дубли webhook;
- событие без `paid=Y` не отмечает оплату;
- polling обнаруживает оплату при потерянном событии;
- graceful shutdown;
- логи не содержат PII и URL.

### Готово, когда

- API не обязан оставаться запущенным для продолжения уже созданной операции;
- потерянный webhook компенсируется polling;
- повторные события безопасны.

8. Генерировать один idempotency key на попытку; не менять его при сетевом
   retry.
9. После `202` опрашивать карточку операции с bounded interval; прекращать при
   terminal state или уходе компонента.
10. При `BX24_CLIENT_AMBIGUOUS` показать кандидатов и отправить выбранный ID.
11. На результате показывать статус, short URL, QR и resend. Не показывать
    «SMS отправлено», пока backend не вернул подтверждённый статус.
12. Удалить UI подключения существующего домофона и создания пользователя.
13. Сохранить мобильную компоновку и доступность кнопок/labels.

### Frontend-тесты

- раздел скрыт без capability;
- адрес выбран и передан;
- адрес пропущен, квартиры нет в payload;
- фильтрация адресов;
- выбор товара и каталожная цена;
- изменение/запрет изменения суммы;
- строковые номера квартир;
- полный happy path;
- повтор submit использует тот же idempotency key;
- восстановление после reload по transaction ID;
- неоднозначный клиент;
- SMS failed при наличии QR;
- resend вызывает только endpoint отправки;
- auth expiry и сетевые ошибки.

### Готово, когда

- старый сценарий «Домофоны» отсутствует;
- мастер полностью работает с mock API;
- повторные клики и навигация назад не создают лишних операций.

## Этап 9. Реальная интеграция SMS и Bitrix24

Этот этап требует заранее подготовленной конфигурации портала и выполняется
после завершения программных этапов.

### Действия

1. Создать/выбрать поле CRM-счёта для платёжной ссылки.
2. Настроить робот Bitrix24, отправляющий SMS по согласованному триггеру.
3. Проверить, какой сигнал подтверждает постановку и доставку SMS.
4. Заполнить `BX24_PAYMENT_LINK_FIELD` и `BX24_PAYMENT_SEND_TRIGGER`.
5. На тестовом контакте выполнить минимальный платёжный сценарий.
6. Проверить кассу, состав чека, пользовательскую цену, доступные платёжные
   системы, SMS, повторную отправку и поступление статуса оплаты.
7. Проверить комментарии и activity в лиде/контакте.
8. Зафиксировать фактический контракт в архитектурном документе и тестовых
   fixtures.

### Стоп-условия

Не переходить к production, если:

- робот требует ручного действия в карточке;
- невозможно отличить queued/sent/failed;
- изменённая цена неправильно попадает в чек;
- ссылка ведёт на другую сумму или товар;
- Bitrix24 создаёт дубли при retry;
- оплата не подтверждается событием или polling.

### Готово, когда

- один сквозной тест прошёл на минимальной сумме;
- внешний тестовый платёж и способ его возврата/закрытия документированы;
- результат SMS не симулируется приложением.
