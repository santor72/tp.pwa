# Права доступа

## Назначение

Доступ в PWA определяется на backend после успешной авторизации в ТехПортале.
Frontend получает готовый набор `capabilities` и использует его только для
отображения элементов интерфейса. Любое действие повторно проверяется сервером.

Не следует использовать скрытие кнопки как защиту: пользователь может вызвать API
напрямую.

## Источники данных

Ответ ТехПортала при входе содержит:

- `status` — статус пользователя;
- `properties.permissions` — точечные права ТехПортала.

Оба значения сохраняются в серверной Redis-сессии. При успешном входе они также
обновляют профиль пользователя в PostgreSQL, поэтому Telegram получает те же
актуальные права, что и PWA.

## Роли

Роль вычисляется только на сервере по значению `status`:

| `status` ТехПортала | Роль приложения |
|---|---|
| `admin` | `admin` |
| `manager` | `manager` |
| любое другое значение, `null` или пустая строка | `user` |

Сравнение не зависит от регистра и пробелов по краям значения. Роль включается в
`user.role` ответов `POST /api/auth/login` и `GET /api/auth/session`.

## Capabilities

В тех же ответах API возвращает объект:

```json
{
  "capabilities": {
    "payments": true,
    "messenger_settings": false,
    "all_tickets": false
  }
}
```

| Capability | Кто получает | Использование |
|---|---|---|
| `payments` | Пользователь с `permissions.client.create === true` | Показ и доступ к разделу «Оплата» |
| `messenger_settings` | `admin`, либо любой пользователь при `MESSENGER_SHOW=true` | Показ «Настроек» и управление привязкой Telegram |
| `all_tickets` | `admin`, `manager` | Показ переключателя «Все заявки» |

Capabilities не принимаются от клиента и пересчитываются при каждом запросе
сессии. При добавлении нового раздела нужно сначала добавить capability на backend,
затем использовать её в PWA и повторить проверку в соответствующем API.

## Заявки

По умолчанию запросы `GET /api/tickets/today` и `GET /api/tickets/tomorrow`
возвращают только заявки, назначенные текущему исполнителю.

Пользователь с `all_tickets` может вызвать:

```text
GET /api/tickets/today?scope=all
GET /api/tickets/tomorrow?scope=all
```

Для остальных ролей такой запрос возвращает `403 PERMISSION_DENIED`. Общий список
предназначен только для просмотра: `can_change_completion` у его карточек равен
`false`. API изменения выполнения дополнительно проверяет назначение заявки текущему
исполнителю, поэтому нельзя изменить чужую заявку прямым запросом.

В режиме `scope=all` карточка показывает поле `assigned_masters`. Это имена
исполнителей, полученные по ID из `masters` заявки через справочник
`techportal-user/list`; неизвестный ID отображается как `Пользователь #<id>`.

В обоих режимах PWA по умолчанию скрывает исполненные заявки. Переключатель
«Закрытые» показывает их вместе с неисполненными; его состояние сохраняется в
`localStorage` браузера.

Переключатель «Все заявки» также сохраняется в `localStorage`. При следующем
открытии PWA он восстанавливается только для пользователя с `all_tickets`; для
остальных всегда используется безопасный режим назначенных заявок.

## Telegram и настройка показа

По умолчанию настройки Telegram видит только `admin`:

```dotenv
MESSENGER_SHOW=false
```

При `MESSENGER_SHOW=true` настройки и привязка Telegram доступны любому
авторизованному пользователю. Переменная передаётся только API-контейнеру; после её
изменения нужно пересоздать API:

```bash
docker compose up -d --force-recreate api
```

Во время переходного периода поддерживается опечатка `MESSENDGER_SHOW`, но для всех
новых конфигураций используйте только `MESSENGER_SHOW`.

Маршруты `GET /api/messenger-links`, `POST /api/messenger-links/telegram` и
`DELETE /api/messenger-links/telegram` сами проверяют `messenger_settings` и
возвращают `403 PERMISSION_DENIED` при отсутствии доступа.

## Ошибки

| HTTP | Код | Значение |
|---|---|---|
| `401` | `AUTH_EXPIRED` | Нет активной сессии или она истекла |
| `403` | `PERMISSION_DENIED` | Роль или точечное право не позволяют выполнить операцию |
| `403` | `CSRF_INVALID` | Некорректный CSRF-токен для изменяющего запроса |
