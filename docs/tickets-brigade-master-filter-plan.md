# Фильтрация всех заявок по бригаде и мастеру

## Решение

В режиме `scope=all` пользователь с capability `all_tickets` может отобрать
заявки выбранного дня по одной или нескольким бригадам и/или мастерам.
Фильтрация выполняется на backend и передаётся в ТехПортал через `masterIds`.
Это не меняет ограничение доступа: общий список остаётся доступным только для
чтения, а изменение выполнения по-прежнему разрешено лишь назначенному мастеру.

Источники справочников ТехПортала:

- `GET techportal-user/list` — полный список пользователей (ID и отображаемое
  имя мастера);
- `GET techportal-user/brigades` — бригады, их ID, название и соответствующие
  IDs мастеров.

## Поведение интерфейса

1. В режиме «Все заявки» видна компактная кнопка «Фильтр» и строка текущего
   выбора. Сам экран фильтра доступен только пользователю с capability
   `all_tickets`.
2. Кнопка открывает отдельный экран с двумя обычными выпадающими списками:
   «Бригады» и «Мастера». В каждом можно выбрать одно значение либо вариант
   «Все»; действие «Сбросить» очищает оба.
3. Изменения применяются к списку только по кнопке «Применить». При отсутствии
   выбора отображаются все заявки выбранного дня.
4. Применённые значения сохраняются в `localStorage` отдельно для пользователя;
   при переходе в режим назначенных заявок они не применяются.
5. После смены фильтра список перезагружается; кнопка обновления повторяет
   запрос с теми же значениями.

## Семантика отбора

- Заявка подходит, если среди её назначенных мастеров есть хотя бы один мастер
  из любой выбранной бригады или один явно выбранный мастер.
- Внутри одного типа выбора и между бригадами и мастерами используется логика
  «ИЛИ».
- Мастер может состоять в нескольких бригадах; это не создаёт дубликатов.
- Заявка с несколькими назначенными мастерами показывается при совпадении
  любого из них.
- Если выбранная бригада не существует, недоступна или не содержит мастеров,
  она не должна превращать запрос в загрузку всех заявок. UI очищает устаревшее
  значение после обновления справочника и сообщает о нём пользователю.

## Контракт API PWA

### Справочник фильтра

`GET /api/tickets/filters`

Доступен только пользователю с `all_tickets`. Ответ не передаёт сведения,
которые не нужны для фильтрации:

```json
{
  "masters": [
    { "id": "87", "name": "Иван Иванов" }
  ],
  "brigades": [
    { "id": "4", "name": "Иванов, Петров", "master_ids": ["87", "112"] }
  ]
}
```

Тип ID на границе API — строка, поскольку ТехПортал допускает числовые и
строковые идентификаторы. Пустые имена нормализуются в `Пользователь #<id>`.
В список `masters` попадают только пользователи, состоящие хотя бы в одной
бригаде из справочника `brigades`.
Поле `brigades[].name` — список фамилий мастеров этой бригады; служебное
название или ID бригады в интерфейс не выводится.

### Список заявок

Расширить существующий endpoint:

```text
GET /api/tickets/today?scope=all&brigade_ids=4,9&master_ids=87,112
GET /api/tickets/tomorrow?scope=all&brigade_ids=4&master_ids=112
```

Параметры допускаются только при `scope=all`. Для `scope=assigned` они
игнорируются либо отклоняются с `422 VALIDATION_ERROR`; рекомендуется второй
вариант, чтобы не создавать ложное впечатление применённого фильтра.

Backend объединяет IDs явных мастеров с участниками выбранных бригад, удаляет
дубликаты и передаёт непустой результат в `tickets/get.filters.and[0].masterIds`.
Если пользователь выбрал фильтры, но после разрешения не осталось ни одного
мастера, backend возвращает пустой список, не опуская `masterIds`.

## Кэширование и отказоустойчивость

- Справочники пользователей и бригад кэшируются в Redis раздельно, с TTL
  5 минут: используется существующий TTL справочника пользователей
  `TP_USERS_CACHE_TTL_SECONDS`.
- Формирование списка заявок использует кэшированный справочник для разворота
  бригад, а также для отображения `assigned_masters`.
- При первом запросе и недоступности ТехПортала возвращается существующая
  контролируемая ошибка upstream; устаревший кэш можно использовать до
  согласованного срока, если такая политика уже поддерживается CacheStore.
- Endpoint справочника и список заявок не должны принимать названия как ключи:
  фильтрация всегда ведётся по ID.

## План реализации

1. **Модели ТехПортала.** Зафиксировать фактическую форму ответа
   `techportal-user/brigades`, добавить Pydantic-схему бригады и тесты
   валидации. Уточнить название поля со списком IDs мастеров по реальному
   ответу.
2. **Клиент ТехПортала.** Добавить метод получения бригад. Расширить
   `TechPortalClient.tickets` опциональным набором `master_ids`; не передавать
   `masterIds` при отсутствии фильтра. Пустой итог выбранного фильтра
   обрабатывается сервисом возвратом пустого списка без запроса к ТехПорталу:
   семантика пустого `masterIds` во внешнем API не должна влиять на доступ.
3. **Сервис заявок.** Добавить кэш бригад, нормализацию справочника и разворот
   `brigade_ids` в IDs мастеров. Явно различить «фильтр отсутствует» и
   «фильтр выбран, но не дал мастеров».
4. **Backend API и права.** Реализовать `GET /api/tickets/filters`, добавить
   query-параметры списка и проверку `all_tickets` до обращения к ТехПорталу.
   Расширить аудит: scope, количество выбранных бригад/мастеров и итоговое
   число заявок, без журналирования имён.
5. **PWA API и состояние.** Добавить типы справочника, загрузку после включения
   `scope=all`, сериализацию ID в query-параметры, сохранение выбора в
   `localStorage` с ключом, привязанным к ID пользователя.
6. **Интерфейс.** Реализовать доступные обычные выпадающие списки со значением
   «Все» и сбросом. Обработать загрузку, ошибку справочника и очищение
   исчезнувших вариантов.
7. **Тесты backend.** Проверить запросы к обоим внешним endpoints, кэширование,
   объединение/дедупликацию IDs, пустую бригаду, несуществующие IDs, запрет для
   обычного исполнителя и отсутствие возможности изменять чужую заявку.
8. **Тесты frontend.** Проверить видимость только в общем режиме, передачу
   параметров, выбор нескольких значений, восстановление состояния, сброс,
   ошибку загрузки справочника и доступность клавиатурой.
9. **Документация и приёмка.** Обновить `docs/permissions.md`, `docs/tickets.md`
   и руководство пользователя. Провести проверку на реальных данных
   ТехПортала для бригад с общими мастерами и заявок с несколькими мастерами.

## Критерии приёмки

- Менеджер или администратор в «Все заявки» может выбрать бригаду, мастера или
  их комбинацию и видит только ожидаемые заявки на сегодня/завтра.
- Обычный исполнитель не видит фильтр, не получает справочник и не может
  применить параметры прямым HTTP-запросом.
- Пустая или удалённая бригада не раскрывает общий список заявок.
- Карточки отфильтрованного общего списка показывают назначенных мастеров и не
  позволяют менять выполнение чужих заявок.
- После перезагрузки страницы выбор фильтра восстанавливается для того же
  пользователя и корректно очищается при изменении справочника.
