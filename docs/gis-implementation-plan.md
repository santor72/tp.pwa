# План разработки интеграции с Точка GIS

Дата: 16.09.2026. Статус: запланировано, реализация не начата.
Основание: [принятая архитектура](gis-architecture.md).

## Правила выполнения

- Выполнять этапы последовательно; отмечать выполненные пункты только после
  проверки и сохранять сведения о проверках и отклонениях.
- GIS разрабатывать в отдельном checkout внешнего репозитория. Не добавлять
  `tochka-gis` или его исходники в репозиторий PWA.
- Обязательный инвариант: отчёт подключения имеет выбранный `feature_id`;
  новый сценарий закрытия отклоняет его отсутствие до обращения на запись в ТП.
- Принятый план не означает разрешение на тестовые отчёты в рабочем GIS,
  закрытие реальных заявок или production-выкладку. Проверять на тестовых данных.
- Каждый этап заканчивается запускаемым результатом и описанными ограничениями.
  Наличие PR, его принятие и установка в GIS — разные состояния.

## 1. PR в GIS: API чтения, токен, отчёты, OpenAPI и тесты

### Подготовка и контракт

- [ ] Определить upstream-репозиторий, целевую ветку, правила вклада и тестовую
  среду; сверить актуальный код с локальным снимком.
- [ ] Создать отдельную ветку/checkout GIS, не изменяя справочный каталог PWA.
- [ ] Согласовать опубликованный набор карт и типы объектов для подключения.
- [ ] Зафиксировать OpenAPI `/integration/v1`: карты, слои, геометрия, поиск,
  карточки, значки, создание и проверка отчёта по внешнему ID.
- [ ] Описать минимальные поля карточек, GeoJSON/WGS84, лимиты, коды ошибок,
  обязательность объекта и семантику повторов.

### Реализация

- [ ] Добавить контекст сервисного клиента и Bearer-проверку отдельно от
  cookie-маршрутов, отзыв/ротацию токена, безопасное хранение проверочного значения.
- [ ] Реализовать фиксированный набор операций: чтение и добавление отчёта,
  без правки объектов и обхода защиты существующего API.
- [ ] Выделить необходимые общие сервисные функции из браузерных обработчиков.
- [ ] Реализовать чтение опубликованных карт/слоёв/объектов и значков;
  исключить удалённые объекты и лишние служебные поля.
- [ ] Ограничить bbox, масштаб, размер ответа и частоту запросов; явно
  сигнализировать о неполной геометрии.
- [ ] Добавить миграцию внешних идентичностей/квитанций отчётов с уникальностью
  `(integration_client_id, external_report_id)`.
- [ ] Принимать multipart с обязательным объектом, внешним авторством,
  ID заявки/операции и фото; источник определять по токену.
- [ ] Проверять фото и объект, сохранять файлы надёжно до подтверждения приёма;
  предусмотреть очистку и восстановление после частичной записи.
- [ ] Транзакционно сохранять отчёт, квитанцию и одно Telegram-задание;
  не открывать через этот API изменение `closure_full`.
- [ ] Реализовать одинаковые/конкурентные повторы и конфликт содержимого;
  проверку результата по внешнему ID, в том числе после удаления объекта.
- [ ] Добавить request ID, аудит источника, квоты интеграции и диагностику
  без токенов, фотографий и полного текста отчётов.

### Проверки и передача

- [ ] Проверить отсутствие/ошибку/отзыв токена, ротацию без потери идемпотентности,
  недоступность редактирования и неизменность cookie-защиты GIS.
- [ ] Проверить границы области, координаты, поиск, значки, усечение ответа,
  удалённые объекты и отсутствие лишних полей.
- [ ] Проверить отсутствие `feature_id`, чужой/недоступный объект, неверные фото,
  лимиты, внешнее авторство и неизменность геометрии.
- [ ] Проверить одинаковый и конкурентный повтор, конфликт содержимого,
  потерю HTTP-ответа после COMMIT, единственность отчёта и Telegram-задания.
- [ ] Проверить сбои БД/файлового хранилища, отсутствие подтверждения для
  неполного отчёта, восстановление и миграцию существующих данных.
- [ ] Выполнить обязательные проверки GIS и сверить реализацию с OpenAPI.
- [ ] Подготовить PR с миграцией, инструкцией выдачи/замены токена, настройкой
  reverse proxy, тестами и порядком установки/отката.
- [ ] Опубликовать PR в согласованный upstream при наличии доступа;
  зафиксировать ссылку и результаты ревью.

Критерий готовности разработки: проверяемый PR реализует контракт без нарушения
существующего UI GIS. Предпосылка живой интеграционной приёмки этапа 2: API
установлен в тестовом GIS, известны URL и тестовый токен. До установки допускается
разработка PWA на контрактных фикстурах, но она не считается проверкой живого GIS.

## 2. Карта в PWA: адаптер, геолокация, слои, карточка и выбор

### Backend

- [ ] Добавить GIS-адаптер с настройками URL, серверного токена, тайм-аутов и
  ограничений; секреты исключить из ответов и логов.
- [ ] Добавить узкие `/api/gis/*` с текущей проверкой сессии, схемами ответов
  и нормализацией ошибок; не реализовывать произвольный HTTP-прокси.
- [ ] Реализовать карты, слои, область, поиск, карточку и потоковую выдачу
  значков с ограничениями размеров.
- [ ] Определить допустимый короткий кэш и инвалидирование; проверку объекта
  перед закрытием не подменять устаревшим кэшем.

### Frontend

- [ ] Выбрать картографический компонент и подложку, проверить условия,
  атрибуцию, ключ и работу на домене PWA.
- [ ] Добавить вкладку карты, выбор региона и слоёв, загрузку видимой области.
- [ ] Отменять старые запросы, обрабатывать неполный результат, ошибки и
  смену карты; не выдавать усечённую карту за полную.
- [ ] Добавить геолокацию, маркер и точность, повторный запрос положения,
  остановку наблюдения при уходе с экрана.
- [ ] Реализовать ручную работу без геолокации и начальный/сохранённый обзор.
- [ ] Реализовать карточку, поиск и переиспользуемый выбор объекта для формы
  закрытия: явное подтверждение UUID, названия, карты и слоя.
- [ ] Исключить автоматическое назначение ближайшей точки и хранение трека.

### Проверки и документация

- [ ] Проверить адаптер на ответах OpenAPI и тестовом GIS, включая 401/429/5xx,
  тайм-ауты и некорректные ответы upstream.
- [ ] Проверить, что сервисный токен отсутствует в bundle, URL и сетевых
  ответах PWA; анонимное чтение `/api/gis/*` запрещено.
- [ ] Проверить мобильный экран: разрешение/отказ/тайм-аут геолокации,
  смену слоёв, быстрые перемещения, карточки, поиск и выбор объекта.
- [ ] Проверить недоступность GIS и пустую область без ложного успешного UI.
- [ ] Обновить конфигурационную документацию и пользовательское описание карты.

Критерий готовности: авторизованный монтажник видит живую карту через наш backend,
может определить своё положение или работать вручную и подтвердить объект сети.
Проверка на физическом мобильном устройстве фиксируется отдельно от эмуляции.
Этот этап ещё не включает отправку отчёта при закрытии.

## 3. Закрытие с отчётом: хранение, очередь, сверка и интерфейс

### Модель и внешние предпосылки

- [ ] Проверить фактическую семантику `tickets/persist`, перечитывание по ID,
  повторное закрытие, конкурентное изменение тегов и неопределённый ответ.
- [ ] Зафиксировать критерии автоматической сверки и перехода в ручной разбор;
  не предполагать, что один текущий признак «закрыто» доказывает нашу операцию.
- [ ] Спроектировать отдельные GIS-таблицы операций, снимков отчётов,
  вложений и outbox; индексы, миграции и ограничения конкурентных закрытий.
- [ ] Зафиксировать цикл повторного открытия/закрытия и правила новой
  идентичности отчёта; сетевой повтор сохраняет исходную идентичность.
- [ ] Настроить постоянное приватное хранение фото, лимиты, резервирование,
  удержание до доставки и очистку осиротевших загрузок.

### Прикладной процесс

- [ ] Расширить форму подключения: обязательный подтверждённый объект,
  текст/фотографии, состояние загрузки и понятные ошибки.
- [ ] Проверять на backend исполнителя, актуальный тип/состояние заявки,
  `feature_id`, доступность объекта и сохранность вложений до закрытия.
- [ ] Блокировать отсутствие объекта серверной ошибкой без записи в ТехПортал.
- [ ] Сохранять операцию и неизменяемый снимок до внешнего вызова; после
  подтверждения закрытия транзакционно создавать задание доставки.
- [ ] Реализовать состояние неопределённого закрытия и сверку по ID заявки,
  независимо от текущего дня и активной сессии пользователя.
- [ ] Реализовать worker: аренда, конкурентный захват, восстановление после
  перезапуска, backoff/jitter, классификация ошибок и ручной повтор.
- [ ] Отправлять стабильный внешний ID; после потери ответа проверять результат
  в GIS либо повторять неизменный запрос без создания дубля.
- [ ] Обработать удаление объекта после начала закрытия без автоматической
  перепривязки; определить процедуру явного исправления отклонённого отчёта.
- [ ] Показывать раздельные статусы закрытия и доставки, возвращать сохранённую
  операцию при повторном нажатии, восстанавливать экран после перезагрузки.
- [ ] Добавить доступный ответственным разбор `needs_review/needs_attention`
  и повтор доставки с аудитом; не давать обходить проверки заявки.
- [ ] Проверить все текущие каналы и endpoints закрытия: обязательный объект
  нельзя обойти старым запросом после включения нового сценария.

### Проверки устойчивости

- [ ] Нет объекта / объект не существует: нет отчёта и нет закрытия в ТП.
- [ ] Частично загружены фото / нет места: закрытие не началось.
- [ ] GIS недоступен после подготовки: подтверждённое закрытие сохраняется,
  отчёт ждёт доставки и виден в статусе.
- [ ] ТехПортал вернул тайм-аут после записи: сверка восстанавливает результат
  либо требует разбора; отчёт не отправляется преждевременно.
- [ ] Перезапуск перед/после вызова ТП и перед/после записи outbox:
  намерение и вложения сохраняются, операция возобновляется.
- [ ] GIS сохранил отчёт, но ответ потерян: остаётся один отчёт.
- [ ] Два нажатия / два worker / истекшая аренда: отсутствуют дубли операции
  и отчёта, подтверждённые результаты не перезаписываются запоздалым worker.
- [ ] Объект удалён или токен отозван: понятная ошибка, снимок и фото сохранены.
- [ ] Повторное открытие и новое закрытие: новая осмысленная операция,
  старые отчёты остаются в истории.
- [ ] Заявка перешла на другой день, сессия истекла: фоновая обработка продолжается.
- [ ] Регрессия: ремонты, действующие проверки принадлежности и CSRF,
  платежи и штатная работа GIS не нарушены.

### Эксплуатация и включение

- [ ] Добавить метрики возраста очереди, повторов, неопределённых закрытий,
  ошибок токена и доставки; корреляцию по ID без чувствительного содержимого.
- [ ] Подготовить runbook: настройка токена, запуск worker, диагностика,
  сверка, ручной повтор, хранение фото, backup/restore и обновление.
- [ ] Описать rollout и откат: остановка новых операций не удаляет старые;
  обработка уже принятых заданий должна продолжаться.
- [ ] Провести сквозную приёмку на тестовой заявке и объекте с контролируемыми
  сбоями; проверить запись отчёта и существующую маршрутизацию Telegram отдельно.
- [ ] Зафиксировать результаты, остаточные ограничения и отдельное решение
  о production-включении.

Критерий готовности: подключение через новый процесс нельзя закрыть без
выбранного объекта и сохранённого отчёта; после подтверждения ТП отчёт либо
доставлен один раз в GIS, либо устойчиво хранится с объяснимым статусом и
возможностью восстановления. Сбой сети или перезапуск не теряет намерение,
фотографии и результат операции.
